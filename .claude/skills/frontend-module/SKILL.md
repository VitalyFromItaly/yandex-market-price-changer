# Архитектура фронтового модуля (CRM продавца Яндекс.Маркета)

CRM — вторая SPA рядом с админкой `web/`: исходники в `crm/src`, Nest отдаёт сборку по `/crm/`.
Код организован **модулями** в `crm/src/modules/`. Один модуль — одна доменная область (`auth`,
`orders`, `profit`, `settings`, `profile`, …). Следуйте правилам ниже точно.

> Каркас `crm/` — Vite 5, Tailwind, кит примитивов, `crm/src/shared/`, роутер и сайдбар —
> **создаётся в TASK-069**. Эталонного модуля пока нет: первый модуль, написанный по этому скилу
> (`auth` в TASK-071), становится образцом для остальных.

## Только строгое равенство

Всегда `===` / `!==`. **Никогда** `==` / `!=`, включая идиому `x == null`. Для nullable — `x ===
null || x === undefined` (или сузьте тип, чтобы хватило `=== null`).

## Когда применять

- Новый модуль (`orders`, `profit`, `settings`, …).
- Новые store, api-клиент, composable, mapper, constants или компонент в существующем модуле.
- Ревью фронтового кода на соответствие конвенции.

## Раскладка

```
crm/src/modules/<module-name>/
├── <module-name>.domain.ts     # ОБЯЗАТЕЛЬНО: доменные типы/интерфейсы
├── api/                        # ОБЯЗАТЕЛЬНО: запросы к бэкенду
├── store/                      # ОБЯЗАТЕЛЬНО: Pinia-стор
├── composables/                # ОБЯЗАТЕЛЬНО: переиспользуемая логика (use…)
├── components/                 # ОБЯЗАТЕЛЬНО: Vue-компоненты
├── pages/                      # страницы маршрутов модуля (PascalCase .vue)
│   └── routes.ts               # RouteRecordRaw[] модуля (собирается центральным роутером)
├── mappers/                    # ОПЦИОНАЛЬНО: ответ API <-> домен <-> вид
└── constants/                  # ОПЦИОНАЛЬНО: константы модуля
```

## Общие утилиты (`crm/src/shared/`, TASK-069)

Межмодульные хелперы — в `src/shared/`, не внутри модулей:

- **`shared/composables/useBaseState.ts`** — кортеж `[state, setState, isLoading, resetState,
  hasState]` для реактивного состояния слайсов (во всех композаблах стора).
- **`shared/store/`** — `resettableStoresPlugin` и `resetAllStores()` (выход, 401, смена магазина).
- **`shared/http`** — единственный HTTP-клиент: префикс `/api/crm`, заголовок `Authorization: Bearer`,
  ошибки — `ApiError` со статусом и `code` сервера (`PASSWORD_CHANGE_REQUIRED` и т.п.).
- **`shared/utils/`** — чистые хелперы.

Импорт: `import { useBaseState } from '@/shared/composables'`. Алиас `@` → `crm/src` — только внутри
`crm/`; бэкенд (`src/`) по-прежнему на относительных импортах.

## Маршрутизация — страницы в модуле, маршруты собираются

- Страницы маршрутов — в `src/modules/<module>/pages/` (PascalCase `.vue`).
- Каждый модуль объявляет маршруты в `pages/routes.ts`, экспортируя именованный `RouteRecordRaw[]`
  (`export const ordersRoutes = [...]`). `routes.ts` — единственный файл, освобождённый от суффикса.
- Центральный `src/router/index.ts` импортирует массивы модулей и спредит их; там же корневой
  редирект и глобальный гард авторизации (и гард смены пароля). Отдельные маршруты фич инлайн там
  **не** объявляются.
- **Роутер на `createWebHashHistory`** — довод админки: F5 на `#/ym/orders` не уходит на сервер, и
  не нужен SPA-fallback, который мог бы проглотить ошибку `/api`.
- **Маршруты фич маркетплейса — под `/ym/...`** (`/ym/orders`, `/ym/profit`, `/ym/settings`): другие
  маркетплейсы — только каркас, но префикс закладывается сразу, чтобы потом не переписывать ссылки.
  Вне префикса — то, что не про маркетплейс: вход, смена пароля, профиль.
- Страницы грузятся лениво в `routes.ts` через `() => import('@/modules/<m>/pages/<Page>.vue')`.
  Публичные маршруты (вход) — `meta: { public: true }`.
- **Вкладки внутри страницы живут в URL.** Активная вкладка `Tabs` хранится в URL, а не только в
  локальном `ref`, чтобы перезагрузка или ссылка открывали ту же вкладку. **Предпочтительно —
  параметр пути `:tab?`**: модель `Tabs` — writable `computed`, сеттер делает `router.replace`
  (`replace`, не `push`) и опускает параметр для вкладки по умолчанию. `?tab=` — только где сегмент
  пути невозможен (несколько независимых групп вкладок). Голый `v-model="activeTab"` на `ref` — баг.
  Когда такой паттерн понадобится второй раз — вынесите его в `shared/composables`.
- `<module-name>` — **единственное число, kebab-case**, кроме устоявшихся доменных имён во
  множественном (`orders`, `settings`): имя модуля совпадает с тем, как область называется в API
  (`/api/crm/ym/orders`).

## Именование файлов (стиль NestJS)

1. **Каждый `.ts` в модуле оканчивается на `.<module-name>.ts`.** Сначала описательное имя, суффикс
   модуля последним:
   - `mapOrder.orders.ts`
   - `ordersApi.orders.ts`
   - `store.orders.ts`
   - `useOrders.orders.ts`
   - `orderStatus.orders.ts`
2. **Доменные типы — в `<module-name>.domain.ts`** (`orders.domain.ts`, `profit.domain.ts`).
   Единственный файл, где имя модуля идёт первым. Интерфейсы, типы ответов API, юнионы.
3. **Vue-компоненты — `PascalCase.vue`** в `components/`, без суффикса: `OrdersTable.vue`,
   `ProfitSummary.vue`, `RatesForm.vue`.

## Слои — компоненты и страницы не зовут api напрямую (обязательно)

- **Компоненты и страницы ходят через стор**, никогда не импортируют `*/api/*`. Поток всегда:
  компонент/страница → стор (действие/геттер) → api.
- **Преобразования данных — в мапперах**, не в компонентах: ответ API → домен (нормализация дат,
  `null` вместо отсутствующего поля) и домен → модель вида (опции `{ value, label }`, строки
  таблицы). `mappers/map<Thing>.<module>.ts`; результат отдаётся стором (геттером) или маппер
  импортируется там, где нужен — но `.map(t => ({ value: t.id, … }))` в компоненте не пишется.
- Только `store/` и `api/` импортируют из `api/`. Композаблы могут звать стор. Слой api — единственное
  место, где есть HTTP (через общий клиент из `shared/http`).
- **Бизнес-логики на фронте нет.** Прибыль, «Продажи», фильтры статусов, окна по 30 дней считает
  бэкенд теми же сервисами, что и бот (решение «одна логика — два канала»). Фронт показывает и
  форматирует. Пересчитанная на фронте цифра — вторая копия формулы, а вторая копия расходится.

## Размер компонента и декомпозиция (обязательно)

`.vue` больше **~300 строк** — не большой экран, а две роли в одном файле. Делите *до* того, как
добавлять. Три хода, в таком порядке; обычно хватает первого подходящего.

**1. Повторяющаяся разметка → дочерний компонент.** Признак — один и тот же набор контролов дважды:
мобильная и десктопная ветки, шапка и строка, форма создания и форма правки. Напишите поля один раз.

Адаптивность — классы видимости Tailwind на **одном** дереве разметки (`hidden md:table-cell`), а не
две ветки за `useMediaQuery`. Две копии — два места, где забыть: одну поправят, другая останется со
старым поведением.

**2. Состояние и действия, которые им владеют → `composables/use<Concern>.<module>.ts`.** Признак —
кластер ref'ов, таймеров и функций, имеющих смысл только вместе: черновик с дебаунсом, машина
состояний диалога, набор записей, каждая из которых кончается `toast.error`.

Это полоса **`composables/` в корне модуля** — она зовёт `useXxxStore()` и импортируется
компонентами. Это **не** `store/composables/`, которые внутренние для стора. Эта граница и принцип
«одна забота = состояние *и* его действия» — в [`pinia-store`](../pinia-store/SKILL.md); ссылайтесь,
не пересказывайте.

Типовая форма действия в таком композабле: `busy → try { await store… ; toast.success } catch {
toast.error } finally { busy = false }`. Реактивный контекст приходит геттером (`() => HTMLElement |
null`), а не ref'ом.

Держите их меньше **~200 строк** и давайте каждому `*.spec.ts` рядом (vitest).

**3. Чистые преобразования → `mappers/`, статические данные → `constants/`.** Признак — функция,
которая не читает ни props, ни ref'ы: подпись статуса по коду, список опций из словаря.

В SFC остаются props, композаблы, которые он связывает, и разметка. Компонент, который только
оркестрирует, читается одним экраном.

### Как разбить разросшийся компонент

1. Выпишите `ref`'ы и функции, отметьте, какая функция трогает какой ref.
2. Сгруппируйте по **истории**, а не по виду: «черновик и всё, что его сохраняет», «диалог и две его
   записи». Группа, не делящая состояние с остальными, — это композабл.
3. Сначала вынесите повторяющуюся разметку — обычно самый крупный и безопасный выигрыш.
4. Переносите по одной группе в `composables/use<Concern>.<module>.ts` со спекой, держа компонент
   зелёным между шагами.
5. Остановитесь, когда SFC — только проводка. Если группа не выносится, потому что читает три
   несвязанных ref'а, — компонент держит две роли: разделите компонент и попробуйте снова.

**Компоненты строк принимают явные props и типизированные emits.** Никаких `provide`/`inject` для
контекста строки. Флаг права на правку называется **`editable`**.

**При разбиении `aria-label` переезжают дословно** — это доступное имя контрола, и на нём держатся
тесты компонентов, если они появятся.

**Контроль.** Правила `vue/max-lines-per-block` и `max-lines` для `crm/src/modules/**` заводятся в
`eslint.config.js` вместе с каркасом (TASK-069) — **предупреждениями**, чтобы долг не блокировал
несвязанную работу. Предупреждение — повод разделить, а не число для подкрутки: поднять лимит,
чтобы оно замолчало, — единственный неправильный ответ.

## Данные — по открытию, а не «на всякий случай» (обязательно)

Пока сайдбар, модалка, поповер, раскрытие строки или секция **не открыты** — запроса за их данными
быть не должно. Контейнер живёт на каждом экране раздела, а открывают его редко: загрузка на
`onMounted` превращается в обращение к серверу на каждый переход ради того, что человек не смотрит.
Здесь это ещё и квоты: почти каждый запрос CRM — это запросы к Partner API продавца, а у части
методов лимит 10 в час.

```ts
// ✅ грузим в обработчике открытия
async function openBreakdown(): Promise<void> {
  breakdownOpen.value = true;
  await fetchBreakdown();   // слайс не повторит запрос, если уже загружено
}

// ❌ onMounted(() => void fetchBreakdown())
```

Справочники, меняющиеся только с выкладкой, можно поверх ленивости кешировать в `localStorage` —
**всегда с TTL** (сутки — разумный потолок) и с мягким падением: приватный режим и переполнение
квоты — промах, а не ошибка экрана. Общего хелпера пока нет; понадобится — в `shared/utils`.

Упавший запрос **не** превращает кнопку в мёртвую: контейнер открывается и показывает в себе
состояние ошибки. Клик, после которого ничего не происходит, читается как сломанный UI.

**Открытие контейнера не ждёт ответа.** «Лениво» — про то, ЧТО запрашивать, а не когда показать:
сначала кадр с шапкой и скелетоном, данные приезжают в уже открытый контейнер.

## Конвенции внутри файлов

- **Домен vs ответ API.** API CRM (Nest) уже отдаёт camelCase, так что маппер нужен не для
  snake→camel, а чтобы компоненты не зависели от формы ответа: строки дат → то, что нужно для
  отображения, отсутствующие поля → явный `null`, коды статусов → доменные юнионы. Типы ответа
  (`…Response`) и доменные типы — в `<module>.domain.ts`.
- **`null` — это «неизвестно», а не ноль.** Неизвестная себестоимость, отсутствующая дельта цены —
  `null` и отдельная строка на экране, никогда `?? 0` (довод `orderPurchase` из CLAUDE.md).
- **api/**: тонкие функции поверх общего HTTP-клиента, возвращают **доменные** типы (маппер
  применяется здесь). `<module>Api.<module>.ts` с сгруппированным объектом.
- **store/**: Pinia через `defineStore('<module>', …)`; файл `store.<module>.ts`. Архитектура —
  [`pinia-store`](../pinia-store/SKILL.md): логика в `store/composables/use<Concern>.<module>.ts`,
  фасад тонкий. **Любой стор с состоянием отдаёт собранный `reset()`**, чтобы его чистили выход и
  смена магазина — закладывайте сразу.
- **composables/**: `use<Thing>.<module>.ts`; никаких импортов внутренностей чужого модуля — только
  его публичные api/store.
- **constants/**: enum-as-const, словари подписей, списки опций, типизированные доменными юнионами.
  Подписи, которые уже есть в боте (названия отчётов, статусов), должны совпадать с ботом дословно.
- **`v-model` vs управляемая форма (`:model-value` + `@update:model-value`):** `v-model` — только
  когда значение — **ваше локальное состояние** и связь чистая (без побочных эффектов). Управляемая
  форма — когда у изменения есть **побочный эффект** (сохранение через действие стора / `PATCH`) или
  значение принадлежит другому (prop, поле стора). Никогда не `v-model` prop или поле объекта стора:
  это мутирует чужое состояние на месте и пропускает сохраняющее действие. Нужна эргономика
  `v-model` с эффектом — writable `computed`, чей сеттер зовёт асинхронное действие (пример:
  переключатель рассылки отчёта, который сразу сохраняет расписание).

## Шаги создания модуля

1. `crm/src/modules/<module-name>/`.
2. `<module-name>.domain.ts` — доменный интерфейс и тип ответа API.
3. `mappers/map<Name>.<module>.ts` — ответ → домен.
4. `api/<module>Api.<module>.ts` — возвращает доменные типы (через маппер).
5. `store/store.<module>.ts` (Pinia) — состояние + действия, по `pinia-store`.
6. `composables/use<Name>.<module>.ts`, если нужна переиспользуемая логика.
7. `components/<Name>.vue` для UI, `pages/<Page>.vue` + `pages/routes.ts`, пункт в сайдбаре.
8. `mappers/` и `constants/` — только если реально используются.

## UI-компоненты — никакого сырого HTML в коде фич (обязательно)

Компоненты и страницы фич (`src/modules/**`) не содержат сырой повторяющейся разметки с классами
Tailwind (`div`/`ul`/`li`/`span`/`form`/`select`/`p`/`h1` со стилями). Каждый UI-элемент выносится в
**переиспользуемый примитив** в `crm/src/components/ui/<name>/` (стиль shadcn-vue: копия в проект,
`cn()`, варианты cva, основа reka-ui) и переиспользуется. В идеале фичи состоят только из
компонентов.

> Этот скил — про **структуру** (где лежит код, какой примитив взять). **Визуальные и UX-решения** —
> раскладка, плотность, состояния, тексты, токены — в [`frontend-design`](../frontend-design/SKILL.md).

Кит на старте (TASK-069; расширяйте его, а не пишите разметку заново):
`Button`, `Input`, `Card`, `Table` (+ `TableHeader`, `TableBody`, `TableRow`, `TableHead`,
`TableCell`), `Dialog`, `ConfirmDialog`, `Badge`, `Tabs`, `DropdownMenu`, `Tooltip`, `Toast`,
`Skeleton`, `PageHeader`. Нет нужного (`Label`, `FormField`, `Select`, `EmptyState`, `Stack`,
`Heading`, `Text`…) — сначала добавьте его в кит.

## Списки записей — только Table (обязательно)

Любой **однородный список записей** (заказы, возвраты, отзывы, позиции карантина, бренды со
скидками, расписание отчётов) рисуется через `@/components/ui/table` — не списком `List`/`ListItem`
и не вертикальной стопкой `Card`.

**Шаблон:**

1. `Skeleton` / `EmptyState`, пока пусто или грузится.
2. `Card class="p-0"` вокруг `Table` (во вложенных панелях: `rounded-lg border border-border
   overflow-hidden` + `Table`).
3. `TableHeader` с человеческими названиями колонок; главный идентификатор — `RouterLink`, если есть
   куда перейти. Деньги и количества — справа, `tabular-nums`.
4. Действия строки — в **последней** колонке, `Button variant="ghost" size="sm"`.

**Исключения** (таблицу не навязывать): сводка отчёта (ключевые числа и разбивка), карточка одного
отзыва с формой ответа, однострочные формы.

## Основное действие страницы (обязательно)

Главное действие страницы (выгрузить xlsx, загрузить прайс, пересобрать отчёт) — в слоте **`#actions`
у `PageHeader`**, а не в теле страницы и не продублировано в `EmptyState`.

- Основное — `Button` варианта по умолчанию в `#actions`.
- Вторичные — `variant="outline"` в `#actions`; больше двух — в меню `⋯` (см. `frontend-design`).
- `EmptyState` может объяснить, почему пусто, но не держит основную кнопку, если её может показать
  шапка.

## Диалоги — никаких нативных alert/confirm/prompt (обязательно)

Никогда `window.alert`, `window.confirm`, `window.prompt` в коде фич. Модалки из
`@/components/ui/dialog`:

- **`ConfirmDialog`** — да/нет (`@confirm`, `v-model:open`)
- **`Dialog`** — своё тело, когда нужно

Подтверждение обязательно перед всем, что меняет мир за пределами нашей базы: ответ на отзыв
(публичный), подтверждение цены в карантине, запись остатков.

Правила:
- Перед разметкой в фиче проверьте `crm/src/components/ui` на подходящий примитив; нет — сначала
  создайте его там. Примитивам HTML можно — они и есть абстракция.
- Импорт примитивов — из индекса папки: `import { Card } from '@/components/ui/card'`.

## Чеклист перед завершением

- [ ] Папка — `crm/src/modules/<module>/`.
- [ ] Типы — в `<module>.domain.ts`; больше нигде доменные типы не объявляются.
- [ ] Каждый `.ts` оканчивается на `.<module>.ts` (кроме `pages/routes.ts`).
- [ ] Компоненты — `PascalCase.vue` в `components/`.
- [ ] Преобразование ответ↔домен — в маппере, не в компоненте; бизнес-формул на фронте нет.
- [ ] Нет `window.alert` / `window.confirm` / `window.prompt` — только `ConfirmDialog` / `Dialog`.
- [ ] Списки записей — `Table`, не `List`/`ListItem`.
- [ ] Ни один `.vue` не перерос ~300 строк: повторяющаяся разметка — дочерний компонент, логика с
      состоянием — `composables/use<Concern>.<module>.ts` со спекой; новых предупреждений
      `vue/max-lines-per-block` нет.
- [ ] `campaign_id` / `business_id` / токен не попадают на экран.
- [ ] **После любой правки UI/UX:** vitest-спеки сторов и композаблов добавлены или обновлены, и экран
      проверен руками в браузере (`npm run dev:crm`) — счастливый путь, пусто, ошибка, тёмная тема,
      узкая ширина. E2E-инфраструктуры (Playwright) в проекте нет — решение по TASK-068.
- [ ] `npm run typecheck:crm`, `npm run lint` и `npm run test:crm` зелёные (скрипты — TASK-069).
