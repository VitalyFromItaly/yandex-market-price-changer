# Pinia store — атомарные композаблы (CRM продавца)

Каждый Pinia-стор — **одна точка входа**. Бизнес-логика живёт в **атомарных композаблах** в
`store/composables/` — одна логическая забота на файл (загрузить отчёт, сохранить ставки, загрузить
прайс и т.п.). Так стор проще расширять, понимать и тестировать.

Структура модуля, имена файлов и правило «компоненты не зовут `api/` напрямую» — в
[`frontend-module`](../frontend-module/SKILL.md).

> `useBaseState`, `resettableStoresPlugin` / `resetAllStores` и http-клиент **создаются в
> TASK-069** (`crm/src/shared/`). Эталонного модуля пока нет: первый стор, написанный по этому скилу
> (`auth` в TASK-071), становится образцом для остальных.

## Когда применять

- Новый `store/store.<module>.ts`.
- Новое состояние или действие в существующем сторе.
- Разбиение монолитного стора на композаблы.
- Ревью кода стора.

## Раскладка

```
crm/src/modules/<module>/store/
├── store.<module>.ts              # тонкий фасад — ТОЛЬКО собирает слайсы
└── composables/
    ├── use<Concern>.<module>.ts   # одна забота = один атом
    └── use<OtherConcern>.<module>.ts
```

**Важно:** композаблы в `store/composables/` — **внутренние для стора**. Их импортирует только
`store.<module>.ts`. Компоненты и композаблы вида (`composables/use*.ts` в корне модуля) используют
**`useXxxStore()`**, никогда эти атомы напрямую.

## Основные правила

1. **Стор = фасад.** В `store.<module>.ts` нет бизнес-логики — только `defineStore`, импорт
   композаблов, композиция и возврат публичного API.
2. **Одна забота на композабл — состояние и действия вместе.** Слайс владеет своими ref'ами *и*
   функциями, которые их меняют. **Не** делите искусственно на `useXxxState` + `useXxxMutations` с
   проводкой (`useMutations(state.items)`). Делите, только когда заботы действительно независимы
   (отчёт «Прибыль» и ставки, которыми он считается).
3. **Публичный API сохраняется.** Рефакторинг не ломает потребителей: компоненты пользуются
   `useXxxStore()` / `storeToRefs` с теми же ref'ами и действиями. Внутренние хелперы (`key`, `apply`,
   `replace`, `refreshOne`, `setSession`) не экспортируются.
4. **HTTP — только в атомах через `api/`.** Атомы зовут `../api/<module>Api.<module>` (или
   `@/modules/.../api/...` для чужого модуля). Компоненты не импортируют атомы стора.
5. **Доменные типы — из `<module>.domain.ts`.** Атомы работают с доменными моделями, не с сырыми
   ответами API.
6. **Реактивное состояние — через `useBaseState`** (`@/shared/composables`, TASK-069), а не голым
   `ref()`. Шаблон: `const [items, setItems, , resetItems, hasItems] = useBaseState<T[]>([])`.
   `setItems(payload)` — для полной замены; мутации `.value` на месте допустимы для словарей и
   `.push`. Сеттеры не экспортируются. Исключения — слайсы на `useStorage` (тема, свёрнутый сайдбар)
   и слайсы без состояния.
7. **Каждый стор с состоянием отдаёт `reset()`.** Каждый слайс возвращает `reset()` из своих
   `resetState` (4-й элемент кортежа); фасад собирает один общий `reset()` (см. шаблон ниже).
   `resettableStoresPlugin` (подключается в `main.ts`) сам регистрирует любой стор с `reset()`, и
   `resetAllStores()` чистит их:
   - **на выходе** — кнопка «Выйти» и ответ 401 с любого запроса;
   - **при смене магазина** — сессия одна, а магазинов у продавца несколько: отчёт одного магазина
     не должен мелькнуть под именем другого.

   **Пишите новые сторы сразу с `reset()`**, не оставляйте состояние, переживающее сессию или
   магазин. `auth` — единственное осознанное исключение: у него свой `clear()`, и `reset()` у него
   нет (иначе смена магазина разлогинивала бы).

## Кэш экрана и фоновое обновление

Экран открывается с прошлыми данными и обновляется фоном — запрос при открытии уходит всегда.
Хранится в памяти вкладки и в localStorage (`@/shared/cache`, поверх vueuse `useStorage`).

- **Фоновые отчёты** — ничего делать не надо: `useReportJob` кэширует свой результат по ключу из
  `spec.launch` (kind + магазин + params) и отдаёт `data` (свежий или сохранённый для ЭТОГО
  запроса), `isRefreshing`, `savedAt`, `isFresh`. Отчёт-файл по кнопке — `persist: false`.
- **Простая загрузка (один GET)** — состояние через `usePersistedState(() => scope)` вместо
  `useBaseState`: `{ value, savedAt, isLoading, isRefreshing, set, reset }`. Scope с `store`, если
  данные магазинные; живое значение помнит свой ключ и под чужим не показывается.
- Ключ несёт id продавца (`setCacheOwner` ставит `installAuth`): без сессии кэша нет. Выход и 401
  зовут `clearReportCache()` рядом с `resetAllStores()`.
- `reset()` чистит **память**, не localStorage: смена магазина меняет ключ, чужое не мелькнёт.
- **Не кэшировать**: формы, которые берут значения из стора (`useSettings` — свежий ответ стёр
  бы начатую правку), вид открытого магазина (`useStoreContext` — он решает доступ к разделам),
  поиск с пагинацией (`usePurchasePrices`).
- `ensure`/`load` при открытии — всегда запрос; не дублировать только идущий.

## Имена композаблов

| Шаблон | Ответственность | Примеры |
|--------|-----------------|---------|
| `use<Domain>` | одна фича: состояние + её действия | `useOrders`, `useRates`, `useReturns` |
| `use<SubDomain>` | независимая подфича большого стора | `useBrandDiscounts`, `useProfitReport` |
| `use<Capability>` | сквозная способность со своим состоянием | `useAuthSession`, `useReportJob` |

Имя описывает **одну** работу. Доменный язык лучше, чем `useStoreLogic` или механическая пара
`List` / `Mutations`.

Имя файла: `use<Name>.<module>.ts` (правило суффикса, как у остальных `.ts` модуля), например
`useOrders.orders.ts`, `useProfitReport.profit.ts`, `useRates.settings.ts`,
`useAuthSession.auth.ts`.

## Один композабл или несколько

| Ситуация | Композаблы |
|-----------|-------------|
| Маленький стор, одна сущность/поток | **1** — `useOrders`, `useAuthSession` |
| Большой стор, разные области UI | **2–6** по домену — `settings`: ставки, скидки по брендам, расписание |
| Общий ref нужен только для проводки | **слить** в один композабл вместо List+Mutations |

**Антипаттерн:** `useRatesList` + `useRatesMutations(rates)` — если мутации существуют только ради
этого списка, им место в том же композабле (`useRates`).

## Шаблоны композиции

### Шаблон A — независимые слайсы с общим `reset()` (по умолчанию)

Каждый слайс — в именованную константу, спред, и один общий `reset()` **последним ключом** (он
перекрывает `reset` отдельных слайсов, протёкшие через спред). Слайсы без состояния не вызываются.

```ts
export const useSettingsStore = defineStore('settings', () => {
  const rates = useRates();
  const brandDiscounts = useBrandDiscounts();
  const schedule = useReportSchedule();
  return {
    ...rates,
    ...brandDiscounts,
    ...schedule,
    // Общий reset — ОБЯЗАН быть последним, чтобы перекрыть reset слайсов.
    reset() {
      rates.reset();
      brandDiscounts.reset();
      schedule.reset();
    },
  };
});
```

Слайс отдаёт свой `reset()` из захваченных `resetState`:

```ts
/** Ставки прибыли: комиссия, налог, скидка по умолчанию. */
export function useRates() {
  const [rates, setRates, , resetRates] = useBaseState<Rates | null>(null);
  // ...действия...
  function reset(): void { resetRates(); }
  return { rates, /* ...действия..., */ reset };
}
```

> Чистый спред в стрелке (`() => ({ ...a(), ...b() })`) не умеет собрать `reset()` — для стора с
> состоянием используйте блочную форму выше. Тест `reset()` фасада — `*.spec.ts` рядом со стором:
> заполнить, вызвать `reset()`, проверить начальное состояние каждого слайса.

### Шаблон C — прятать экспорт, нужный только для проводки

Лучше **вообще не возвращать** хелперы проводки из композаблов (`key`, `apply`, `refreshOne`
остаются приватными внутри атома или функциями файла).

Если слайс вынужден отдать что-то только для соседа — отрежьте это в сторе:

```ts
const { apply, ...list } = useOrdersList();
const exporting = useOrdersExport(list.orders, apply);
return { ...list, ...exporting };
```

Не перечисляйте публичные поля руками, когда работает спред + отрезание.

## Как разбить монолитный стор

1. Выпишите все **ref'ы состояния** и **действия** стора.
2. Сгруппируйте по заботе (загрузка / изменение / выгрузка / сессия / производные).
3. Один композабл на группу; состояние переезжает вместе со своими действиями.
4. Общий `loading` держите в одном слайсе и передавайте `Ref<boolean>`, если его используют несколько
   загрузок — не делите на два ref'а (ломает API).
5. Перепишите `store.<module>.ts` фасадом; `npm run typecheck:crm && npm run lint`.
6. **Не трогайте компоненты**, если API стора не был неправильным до этого.

Типичные разбиения:

| Стор | Атомы |
|------|-------|
| Маленький (< ~50 строк, одна сущность) | один `use<Domain>` |
| Отчёт с фоновой сборкой | `use<Report>` (параметры + результат) + общий `useReportJob` (постановка, опрос, статус) |
| Настройки | `useRates` + `useBrandDiscounts` + `useReportSchedule` |
| Auth | `useAuthSession` + `useAuthActions` |
| Приложение | `useAppTheme` + `useActiveStore` (выбранный магазин) |

## Чеклист атома

Каждый `use<Concern>.<module>.ts`:

- [ ] Экспортирует одну функцию `use<Concern>()`.
- [ ] Владеет ref'ами/computed через **`useBaseState`** или получает общие ref'ы аргументами.
- [ ] Зовёт только `api/` и чистые утилиты — никаких импортов других сторов.
- [ ] Возвращает плоский объект `{ состояние, действия... }` для спреда.
- [ ] Отдаёт **`reset()`** из своих `resetState` (кроме слайса без состояния).
- [ ] Однострочный JSDoc о заботе.
- [ ] При сбое API бросает `Error` с понятным пользователю русским текстом (сообщение сервера, если
      оно уже человеческое).
- [ ] Покрыт `*.spec.ts` (vitest, рядом с файлом): api замокан, проверены состояние после успеха,
      после ошибки и после `reset()`.

## Чеклист фасада

- [ ] Файл `store/store.<module>.ts`.
- [ ] `defineStore('<moduleId>', () => { ... })` — setup-стор (функциональная форма).
- [ ] В фасаде нет прямых `ref` и вызовов API (только сборка слайсов).
- [ ] Публичный возврат совпадает с тем, чем уже пользуются компоненты.
- [ ] Внутренние хелперы композаблов **не** экспортируются.
- [ ] Отдаёт собранный **`reset()`** (последним ключом), если стор не без состояния.

## Композаблы вида vs композаблы стора

| | `store/composables/` | `composables/` (корень модуля) |
|--|----------------------|------------------------------|
| Назначение | атомы состояния Pinia | оркестрация UI/страницы |
| Кто импортирует | только `store.<module>.ts` | компоненты Vue, страницы |
| Кого зовут | `api/` | `useXxxStore()`, роутер, другие сторы |

Эти папки не сливаются.

## Антипаттерны

- ❌ 200+ строк логики внутри колбэка `defineStore`.
- ❌ Компоненты импортируют `store/composables/useXxx`.
- ❌ **`useXxxState` + `useXxxMutations(state.ref)`** — состояние и его действия живут в одном композабле.
- ❌ Один гигантский `useEverything` в **большом** сторе с несколькими областями — делить по UI/домену.
- ❌ `apply`, `refreshOne`, `key` в публичном API стора.
- ❌ Один и тот же `ref` в двух композаблах без причины.
- ❌ Импорт чужого `store/composables/` из другого модуля.
- ❌ Стор с состоянием **без `reset()`** — данные протекают через выход и смену магазина.
- ❌ Общий `reset()` **перед** спредами слайсов (протёкший `reset` слайса его перекроет).
- ❌ Токен или `campaign_id`/`business_id` в состоянии, которое рисуется на экране.

## Проверка

После любой правки стора (скрипты `*:crm` заводит TASK-069):

```bash
npm run typecheck:crm && npm run lint && npm run test:crm
```

Компоненты не импортируют `store/composables`:

```bash
rg "store/composables" crm/src/modules --glob '!**/store/**'
# должно быть пусто
```

E2E-инфраструктуры в проекте нет (решение по TASK-068): вместо Playwright — vitest на сторы и
композаблы плюс ручная проверка экрана в браузере (`npm run dev:crm`).
