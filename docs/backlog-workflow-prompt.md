# Промпт: автономная работа агента по бэклогу

Скопируй текст ниже в CLAUDE.md проекта (раздел «Workflow») или используй как стартовый промпт сессии.
Заполни плейсхолдеры `{{...}}` под свой проект — всё остальное универсально.

---

## Работа ведётся строго по бэклогу

В корне репозитория живёт машиночитаемый бэклог. Он — единственный источник правды о том,
что делать; никакая работа не выполняется в обход него.

**Файлы механизма:**

| Файл | Назначение |
|---|---|
| `tasks.json` | активный бэклог: только невыполненные задачи (pending / in_progress / blocked) + правила работы + справочник решений |
| `tasks.archive.json` | выполненные (done) задачи — история; обратно не возвращаются |
| `progress.md` | журнал сессий в обратной хронологии (новые записи сверху) |
| `progress.archive.md` | старые записи журнала; читать НЕ нужно |

**Если файлов ещё нет — создай их (bootstrap):**

1. Разбей требования (PRD / запрос пользователя / результат аудита кода) на задачи по схеме ниже.
   Задача должна быть закрываемой за одну сессию; крупные куски дели на задачи с `dependencies`.
2. Сгруппируй задачи в майлстоуны M0, M1, … (M0 — стабилизация: сборка, запуск, зелёный typecheck).
3. Создай `tasks.json` по шаблону ниже, пустой `tasks.archive.json` (`{"meta": {}, "tasks": []}`)
   и `progress.md` с шапкой «Журнал работ, записи в обратном порядке».
4. Покажи бэклог пользователю на подтверждение, потом входи в обычный цикл.

### Схема tasks.json

```json
{
  "meta": {
    "project": "{{одно предложение: что это за проект}}",
    "prd_source": "{{откуда взяты требования и от какой даты}}",
    "generated_at": "YYYY-MM-DD",
    "milestones": { "M0": "Стабилизация — …", "M1": "…" },
    "active_tasks": 0,
    "archived_tasks": 0,
    "archive_file": "tasks.archive.json"
  },
  "agent_instructions": { "...": "скопируй разделы before_start / during_work / before_finish из этого промпта" },
  "reference": {
    "_описание": "доменные знания и РЕШЕНИЯ ЗАКАЗЧИКА с датами: лимиты API, форматы данных, договорённости. Всё, что агент иначе переспрашивал бы или молча откатывал.",
    "decisions": {}
  },
  "tasks": [
    {
      "id": "TASK-001",
      "milestone": "M0",
      "category": "infrastructure | functional | ui | integration | refactor | deprecation | unit | e2e",
      "priority": "critical | high | medium | low",
      "description": "Что сделать и ПОЧЕМУ (какой дефект/потребность закрывает)",
      "acceptance_criteria": ["проверяемые утверждения о результате"],
      "test_steps": ["Шаг 1: … — как проверить руками/командами, как пользователь, а не только юнитами"],
      "dependencies": ["TASK-000"],
      "status": "pending"
    }
  ]
}
```

Статусы: `pending`, `in_progress`, `done`, `blocked`, `obsolete`.

### Цикл работы

**before_start — выбор задачи:**

1. Прочитай `tasks.json` и `git log --oneline -20`.
2. Прочитай `progress.md` — контекст последних сессий (архив журнала не читай).
3. Выбери **ОДНУ** задачу со статусом `pending` и наивысшим приоритетом
   (critical > high > medium > low).
4. Проверь, что все задачи из `dependencies` выполнены. Если id зависимости
   **отсутствует** в `tasks.json` — она в архиве и считается done. Если зависимость
   не готова — выбери другую задачу.
5. При равном приоритете предпочитай меньший id (раньше по майлстоуну).

**during_work — выполнение:**

- Работай ТОЛЬКО над выбранной задачей. Не трогай несвязанный код.
- Стек и команды проекта: {{стек, версии, тест-раннер — например: «NestJS 11 + Mongoose 8, тесты vitest»}}.
- Доменные правила проекта: {{жёсткие инварианты, которые нельзя нарушать — например:
  «все запросы скоупить по tenant_id», «секреты только через ConfigService»,
  «порядок регистрации обработчиков значим», «deprecated-код не развивать и не удалять»}}.
- Ошибки не глушить: пробрасывать туда, где их видит retry-механизм или общий catch.
- Коммить после каждого логического изменения с осмысленным сообщением.

**before_finish — закрытие задачи:**

1. Выполни **ВСЕ** `test_steps` задачи end-to-end — как пользователь, а не только юнит-тесты.
2. Прогони проверки проекта: {{команды — например: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`}}. Всё должно быть зелёным.
3. Меняй `status` на `done` **ТОЛЬКО** после успешного прохождения всех test_steps.
4. Напиши запись в `progress.md` (сверху): дата, id задачи, что сделано,
   **ключевые решения с обоснованием** («почему так, а не иначе»), раздел «как проверено»
   и честный раздел «чего проверить не удалось». Если файл разросся (>~500 строк) —
   перенеси записи старше двух недель в `progress.archive.md`.
5. Перенеси задачу из `tasks.json` в `tasks.archive.json` (в конец массива `tasks`),
   обнови счётчики `meta.active_tasks` / `meta.archived_tasks`.
6. **ЗАПРЕЩЕНО** удалять или редактировать формулировки задач — менять можно ТОЛЬКО поле
   `status`. Если задача оказалась слишком крупной — не удаляй её: добавь заметку
   в `progress.md` и оставь `pending` (или разбей, добавив новые задачи через intake).

**Continuous loop:** после архивации, записи в журнал и коммитов **СРАЗУ** выбирай следующую
готовую задачу по before_start. НЕ спрашивай «дальше?», «можно продолжать?» и разрешений
между задачами.

**Останавливай цикл ТОЛЬКО если:**

- задача blocked (ждёт внешнего артефакта или решения заказчика);
- нужен явный consent на опасное/необратимое действие (запись в прод, drop базы, деньги);
- нет секретов или инфраструктуры для проверки (боевой API-ключ, туннель, доступ);
- acceptance criteria противоречивы.

В этом случае кратко сообщи причину остановки и жди пользователя.

### Intake: новая работа по ходу сессии

Любую новую работу, о которой пользователь просит в течение сессии, **СНАЧАЛА** оформляй
задачей в `tasks.json`, а не делай ad-hoc в обход бэклога: присвой следующий свободный id,
заполни milestone / category / priority / description / acceptance_criteria / test_steps /
dependencies, статус `pending`, обнови счётчики — и только потом выполняй через обычный цикл.
Исключение — тривиальные правки в рамках уже выбранной задачи.

Решения заказчика (ответы на вопросы, договорённости, «делаем так-то») фиксируй с датой
в `reference.decisions` — иначе следующая сессия переспросит или молча сделает наоборот.

### Требования к записям в progress.md

Запись — не список коммитов, а рассказ для следующей сессии (и следующего агента):

- какую проблему решали и что оказалось её настоящей причиной;
- какие решения приняты и **почему** (включая отвергнутые альтернативы, если выбор неочевиден);
- «как проверено» — конкретно: команды, числа, сверка с живыми данными;
- «чего проверить не удалось» — честно, с причиной (нет доступа, необратимая операция и т.п.);
- находки вне scope — отдельным абзацем, как кандидаты в новые задачи.
