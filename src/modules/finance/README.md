# Финансовый журнал (M16)

Хранилище фактических финансовых операций площадок — основа «фактической прибыли» рядом с плоской
формулой (решение `finance_actual_beside_flat`). Здесь — чистые функции; хранилище — **Postgres**, а не
Mongo (решение `finance_postgres`): схема Drizzle и репозитории в `src/database/postgres/`
(журнал — `finance_operations`, `finance_documents`, `finance_corrections`, `finance_periods`; рядом — сверки,
аномалии, расходы, налоги и закупки). Импорт — `FinanceImportService` (TASK-111).

Правила журнала, классификатора, импорта, ручной загрузки, расписания, сверок, расходов, налогов, ДДС, P&L,
«фактической чистой» и аномалий — в разделе «Доводы и история решений» ниже, вместе с причинами. Выше —
правила разрезов и экранов поверх P&L и журналов Ozon/WB, своих доводов в этом файле у них нет.

## Разрез по товарам (TASK-138, `pnl-sku.ts`)

`pnlOf` сам зовёт `skuBreakdownOf` на тех же строках и той же себестоимости — `pnl.skus`. Правила:

- строка с артикулом — артикулу; без артикула, с заказом — делится по продаже артикулов заказа (без
  продажи — по штукам), веса — по всем строкам входа; без заказа — `rest` («не относится к товару»),
  туда же операционные расходы;
- деление — целыми копейками (`splitKopecks`), Σ = исходной;
- налог — по доле в базе (выручка + прочие доходы по начислению; приближение к `taxOf`);
- Σ чистой товаров + `rest.netKopecks` = `netKopecks` — пинит тест, менять разрез без него нельзя;
- колонки — `SKU_COLUMN_OF`, `Record` по всем статьям; схема — колонка `model` журнала;
- второй потребитель — «Калькулятор цен» (TASK-139): ставки товара за 30 дней берутся из этого же
  разреза, отдельного разреза журнала у него нет. Сборка ставок — `PriceCalcRatesService`
  (`price-calc-rates.service.ts`, помощники — `price-calc-rates.ts`, модуль `FinancePriceCalcModule`): одна на
  CRM-kind `price-calc:rates` и ИИ-инструмент `getPriceFor` (TASK-165, прецедент `InventoryService`);
  `forSku` даёт строку одного товара, товар без продаж в окне — `calcSkuWithoutSales`.
- `FinanceService.monthStatuses` — публичный (TASK-165): им ИИ отличает «журнал месяца не загружен» от нулей
  ДДС и налогового года, которые статуса не несут.

## Продажи по дням и разрезы продаж (TASK-140, `pnl-sales.ts`, `sales-analytics.ts`)

- Ряд по дням (`pnl.salesByDay`) копит `pnlOf` в том же проходе, на тех же строках периода: выручка —
  статьи раздела `revenue`, штуки — `lineUnits` из `cogsOf` (из них же `pnl.units`). Σ дней = итогу по
  построению; второго расчёта нет.
- Заказ — в день своей **первой** строки продажи в периоде, иначе заказ с продажами в два дня посчитался
  бы дважды.
- `pnl.skus.rest.units` — штуки строк без артикула: Σ штук товаров + они = `pnl.units`.
- `salesAnalyticsOf` — свёртка готового `IPnl`: товары (`pnl.skus`), бренды (`brandOf` по названию и
  категории товара, «Остальные» — без бренда), площадки (журнал только ЯМ — строка ЯМ = итог).
  Σ выручки и штук любого разреза + «не относится к товару» = итогу. Заказы складываются в итог только по
  дням: заказ из нескольких артикулов считается у каждого.
- Средний чек и скорость (шт./день за все дни периода) — одна `salesFigures` для итога и строк.

## Сравнение площадок (TASK-137, `marketplace-compare.ts`, `FinanceService.compare`)

- Колонка — P&L площадки из того же `pnlOf`, что «Финансы» (`build` с `marketplace`): выручка, услуги и
  себестоимость равны до копейки. Правил учёта, отличающих сравнение, два: налог по начислению у всех
  (`compare_tax_by_accrual` — принято, когда у Ozon/WB не было `paidAt`; выплаты теперь есть — TASK-184/185,
  правило не пересматривалось) и операционные расходы по доле выручки
  (`compare_opex_by_revenue_share`, `shareAllocation`: делится только итог, Σ долей = расходам кабинета;
  выручки > 0 нигде нет — не делятся, `opexShared: false`).
- `compare` строит P&L дважды на площадку: первый проход без расходов — только выручка для долей. `pnlOf` чистый,
  база читается один раз (`journal`).
- Группы услуг — `service-groups.ts` (`OVERVIEW_SERVICE_GROUP`, `serviceGroupsOf`), общие с «Обзором».
- Схемы — Σ `pnl.skus[].schemes[]` по схеме (`schemeTotalsOf`); строки без товара схемы не имеют, поэтому
  сравнивается маржа, а не суммы. Схема null (WB) не участвует.
- Выводы (`conclusionsOf`) — сравнения чисел; меньше двух площадок с данными или ничья — `reason`, не победитель.
  «Где выгоднее товар» — по общему артикулу, только `costKnown` и штуки > 0.

## Рейтинги и классификации (TASK-141, `sku-ratings.ts`)

- Пороги — только `RATING_THRESHOLDS` (ТОП-20, ABC 0,8/0,95, XYZ 0,10/0,25, неделя 7 дней, от 4 недель);
  экран получает объект в ответе.
- Штуки артикула по дням — `pnl.skuSalesByDay`, тот же проход `pnlOf` и те же `lineUnits`: Σ дней
  артикула = его `units` в `pnl.skus`. Строки без артикула сюда не идут.
- Недели — от `period.from` по 7 дней, неполный хвост не считается; недель меньше 4 — XYZ недоступен с
  причиной. CV = σ (популяционная) / среднее, среднее ≤ 0 — класса нет.
- ABC — класс по доле накопленного итога до товара (< 0,8 — A, < 0,95 — B, иначе C), только значения > 0.
  По прибыли — только `costKnown`; причина отсутствия класса — «нет закупа» / «нет прибыли».
- Рейтинги прибыли и рентабельности, убыточные — только `costKnown`. Спрос — Δ штук к прошлому периоду по
  объединению артикулов (проданный только раньше — падение до нуля).

## Единый склад (TASK-142, `inventory.ts`)

- Строка — товар `Product`; карточка площадки без товара — в `unmatched`, а не теряется.
- Места площадки — `seller` (FBS) и `marketplace` (FBY/FBO/FBW) раздельно; итога «на всех складах» нет.
- Стоимость = (свой склад + склады площадок) × себестоимость; FBS в стоимость не входит — это свой склад.
  Без себестоимости — `withoutCost` (товары и штуки), не ноль.
- Дни запаса — `daysLeftOf` (общий с `purchaseNeedsOf`): без продаж `null`, без остатка 0.
- Продажи — по id товара (журнал Ozon/WB ключуется ключом закупа); `null` у поля — данных нет, не ноль.
- Порог «заканчивается» — `INVENTORY_LOW_DAYS` (14 дней), едет в ответе.

## Лента заказов (TASK-144, `order-feed.ts`, `OrderFeedService`)

- Прибыль заказа = Σ его живых операций журнала − себестоимость. Операции — строки с `orderId` заказа
  (`liveByOrderIds`, индекс `finance_operations_user_order_idx`): ЯМ — id заказа, Ozon — posting_number, WB — srid,
  сводные строки уже разложены `expandBreakdown`. Площадки читаются раздельно: журнал скоупится площадкой.
- `bonus_payment` — справочно, вне суммы, как в P&L.
- Себестоимость — `cogsOf` из `pnl.ts` по строкам заказа, двигающим товар, на день строки (`pnl_cogs_sale_day`);
  закуп — `FinanceService.costOfSkus`, та же дверь, что у P&L. Второго правила себестоимости нет.
- Операций нет — прибыль `null` с причиной `no-operations` (`order_feed_no_ops_null`); у строки товара нет закупа —
  `null` с `no-cost`. Ни то, ни другое не ноль.
- Услуги сводной строки акта ЯМ без номера заказа (хранение, обработка возвратов) в заказ не входят и не
  распределяются (`order_feed_order_ops_only`): у них нет номера, а любая раскладка была бы оценкой. Поэтому расходы
  заказа ЯМ могут не совпасть с листами united-marketplace-services на этих услугах.
- Итоги — по площадке (`IOrderFeedTotals`); общего числа трёх площадок нет.

## Аналитика возвратов (TASK-145, `returns-analytics.ts`, `ReturnsAnalyticsService`)

- Всё — из журнала площадки по дню начисления (`returns_from_journal`): `liveForPnl` → только строки, начисленные в
  периоде (`periodLinesOf` — ридер отдаёт ещё оплаченные в окне строки налоговой базы). Отчёты заказов ЯМ («Едет
  обратно», `collectReturns`) не используются и не меняются: там — возвраты в пути по дате заявки, здесь — во что
  обошлись возвраты периода; смешай источники — штуки и деньги разъедутся по датам.
- Штуки — движением товара строки (`pnlLineOf().goods`) и `cogsOf().lineUnits`, правилом себестоимости P&L. Строка
  возврата баллов ЯМ — `returns` без движения товара: в сумму входит, в штуки нет, поэтому возврат не удваивается.
  Возвращённый заказ — номер строки `returns` в периоде. % = вернулось / выкуплено штук за тот же период; у товара
  может быть > 100 % (возвращают купленное раньше), без выкупов — `null`.
- **Невозвращённая комиссия — нетто по заказу за любые даты** (`returns_unreturned_commission_net_by_order`):
  `liveByOrderIds` по возвращённым заказам, −Σ строк `commission` — удержанная при продаже минус возвращённая (ЯМ —
  «Возврат за размещение товаров на витрине», Ozon/WB — плюсовая часть комиссии в операции возврата). Отдельной
  статьи «возвращённая комиссия» нет ни у одной площадки; по одному периоду продажа прошлого месяца с возвратом в этом
  дала бы «возвращённую» комиссию доходом. Ложится на товар строки возврата заказа.
- **Потери = обратная логистика + удержания + невозвращённые комиссии − компенсации** — одна функция
  `returnLossesOf`. Логистика, удержания и компенсации — все строки статей периода (у сводных и многотоварных без
  артикула — в `rest`): площадки не помечают, к возврату ли относится удержание или компенсация утери.
- Колонки P&L по товару (`SKU_COLUMN_OF`) не годятся: они сворачивают `returns`→выручка,
  `reverse_logistics`→логистика, `withholdings`→прочие услуги. Разрез возвратов — свои корзины по `sku`.
- Хранение и обработка возвратов ЯМ — в сводной строке акта без заказа (`storage`/`processing`): в потери возвратов
  не входят, экран говорит об этом строкой.
- Площадки не смешиваются (`returns_marketplace_switch`): вход — журнал одной площадки, CRM показывает выбранную.

## Прогнозы (TASK-151, `forecast.ts`, `forecast-purchases.ts`)

- Правило одно: факт с 1 числа по вчера + Σ окна базы / N × оставшиеся дни (сегодня — в оставшихся).
  Окно — N дней по вчера (`forecastPlan`), N ∈ 14/28/56. Округление — один раз на показатель (`project`).
- Показатели — `metricsOf(pnl)`: выручка, чистая, штуки, заказы, возвраты, налог и `payable` (что Маркет
  перечислит: `afterMarketplace + cogs`). Год — то же правило от 1 января.
- Месяц окна без строки статуса или окно без выручки — `ok: false` с причиной.
- Рентабельность — 6 закрытых месяцев (незагруженный — `null`) и прогноз текущего.
- Закупки: `⌈скорость × дни запаса − остаток⌉`, не меньше 0; без закупа — счётчиком; первыми — те, что
  кончатся раньше.
- `backtestOf` — то же правило на ряду `salesByDay`, для скрипта `backtest-forecast.ts`.

## Журнал Ozon (TASK-131, TASK-194, `ozon-articles.ts`, `ozon-journal.ts`)

Источник — начисления `/v1/finance/accrual/by-day` (TASK-194; `/v3/finance/transaction/list` Ozon отключил
8.09.2026). Подробности формы и доводы — `src/modules/ozon/README.md`.

- **Площадки не смешиваются** (решение владельца 2026-10-18). Чтения журнала берут `marketplace`
  с умолчанием `'ym'` (`liveForPnl`, `livePaidBetween`, `receivableByArticle`, снятие выпавших):
  экраны и бот видят прежние числа. P&L Ozon — `FinanceService.build(…, {marketplace: 'ozon'})`,
  плоской оценки у Ozon нет (`FLAT_YM_ONLY`). Площадки рядом ставит `FinanceService.compare` (TASK-137,
  раздел «Сравнение площадок» выше); сложения в одно число нет.
- **Строка — начисление, части — `breakdown`.** Статья ставится каждой составляющей: `sale_amount`
  товара — `sales` при плюсе, `returns` при минусе; `commission.commission` — `commission`; сборы с
  `type_id` — по `name` типа из справочника (`ozonAccrualTypeArticle`). Сравнение точное, незнакомое —
  `unknown` и алерт `finance:ozon-articles` (`OzonUnknownArticleError`); у нераспознанной строки
  расшифровка хранится всегда — по ней алерт называет тип.
- **Статья строки целиком** — для чтений без расшифровки: `unknown`, если часть не распознана
  (счётчик статуса периода), иначе `sales`/`returns` по типу строки, иначе статья крупнейшей части.
- **Товар двигает только часть выручки** (`ozonGoodsMovement(type, article)`): части одной операции
  после `expandBreakdown` несут один id, и комиссия той же продажи иначе принесла бы её штуки и закуп
  ещё раз. По той же причине `pnl-sales.ts` и `pnl-sku.ts` берут штуки и закуп по id только у строки
  с `goods`. Штуки у Ozon — Σ `sale_amount / seller_price` товаров отправления, у строк до TASK-194 —
  длина `raw.items` (`COUNT_OF` в репозитории).
- **Общий путь записи — `importBatchAndRecord`**: версия документа, upsert, снятие выпавших,
  корректировки — та же транзакция и тот же `apply`, что у ЯМ. Путь ЯМ (`importPeriod`) не тронут: в
  его транзакции ещё итоги и расшифровка актов. Сверка — та же `reconcile` по заказам из
  `batch.orders` (TASK-132, раздел сверки ниже); площадка без источника (WB) — «не проверен»
  (`RECONCILE_NOT_IMPLEMENTED`). Аномалии — правила ЯМ — не считаются.
- Тип журнала — `FINANCE_REPORT_TYPE[marketplace]` (`ozon-transaction-list`): ключ периода у площадок
  не совпадает.

## Журнал WB (TASK-136, `wb-articles.ts`, `wb-journal.ts`)

Отчёт реализации (`POST finance-api …/sales-reports/detailed`, до 2026 — `reportDetailByPeriod`; строки в прежних именах полей) — по той же схеме, что Ozon: площадка отдельно, путь записи
`importBatchAndRecord`, сверки и аномалий нет (`RECONCILE_NOT_IMPLEMENTED`), тип журнала
`wb-realization-report`.

- **Строка отчёта (`rrd_id`) — операция, денежные колонки — части `breakdown`.** Ключ — `rrd_id` плюс
  сумма (`wbOperationKey`, довод `ozonOperationKey`).
- **Сумма строки — её вклад в «Итого к оплате»**: знак × `ppvz_for_pay` − `delivery_rub` − `storage_fee`
  − `penalty` − `deduction` − `acceptance` + `additional_payment`; знак −1 у `doc_type_name` «Возврат».
  Σ строк одного `realizationreport_id` = к перечислению за неделю (`wbPayoutByReport`, и скрипт импорта
  печатает эту таблицу). `rebill_logistic_cost` в сумму не входит — не проверено (known-gaps).
- **Части**: у товарной строки (`WB_GOODS_OPERS`) — выручка `retail_price_withdisc_rub` (цена продавца
  до СПП, довод «Продаж» WB), эквайринг `acquiring_fee`, комиссия — остаток до `ppvz_for_pay`, поэтому
  Σ частей = сумме по построению. У остальных — блок товара статьёй типа (компенсации).
  `delivery_rub` — `reverse_logistics` при `return_amount > 0`, иначе `delivery_to_buyer`; остальные
  колонки — `WB_COLUMN_ARTICLE`.
- **Незнакомый `supplier_oper_name` — вся сумма одной частью `unknown`** и алерт `finance:wb-articles`:
  что значит блок товара у такого типа, мы не знаем.
- **Товар двигает только часть выручки товарной строки** (`wbGoodsMovement`); штуки — `raw.quantity`
  (`COUNT_OF`).
- **Месяц — по `rr_dt`**: запрос идёт с запасом ±6 дней (`WB_REPORT_MARGIN_DAYS`), в журнал месяца — строки
  с московским днём `rr_dt` внутри (`wbRowsInPeriod`). Неделя на границе ложится в два месяца частями.
- **Артикул — `sa_name` → товар с этой карточкой WB → артикул ЯМ**, иначе `sa_name`. Каталог WB не нужен,
  ключи закупа — в байтах версии (`refreshSku`).

### Финансовые отчёты ЯМ: разведка (M16, TASK-108)

Фактическая прибыль строится из журнала операций площадки (решение `finance_actual_beside_flat`),
и его схему нельзя было проектировать по спеке — у `/returns` форма ответа однажды уже оказалась не той.
`scripts/diagnose-finance.ts` снял структуру пяти отчётов с живого кабинета; **карта «отчёт → лист →
колонки → тип операции → статья» и ключ дедупа — в `reference.decisions`** (`finance_ym_report_map`,
`finance_ym_dedup_key`), не в коде: это данные для TASK-109/110, а не правило рантайма.

- **`format=JSON` — это ZIP**, по JSON-файлу на лист, в каждом `{rows: [...]}`. Разбор — `report-zip.ts`
  (`unzipReportJson`), **`fflate` явной `dependency`**: импорт (TASK-111) живёт в проде, zlib ZIP-обёртку
  не разбирает, а adm-zip есть только через devDependency `onnxruntime-node`, которой нет в прод-образе.
  Транзитивная fflate через `@nestjs/common → file-type` исчезла бы при любом апдейте. `generateReport`
  получил третий аргумент `format` с умолчанием `FILE` — «Отчёты Маркета» не изменились.
- **Журнал — `united-netting`, а не `united-marketplace-services`.** Netting несёт все операции со знаком
  (продажи, субсидии, возвраты, компенсации, удержания за услуги); services — расшифровка услуг по актам.
  Связь проверена до копейки: Σ services за 09-2026 = −Σ строк netting с той же `actDate` (469 903,39 ₽).
  Одна строка netting с `offerOrServiceName = null` — сводное удержание за услуги без заказа (подписка,
  пуши, хранение, вывоз), расшифровать её можно только из services.
- **`Списание` в netting — не деньги**: услуги, оплаченные бонусным балансом совместных акций
  («Справочно: списан с баланса»). В акт они не входят; посчитать их расходом — удвоить услугу.
- **У строк журнала нет id** (`transactionId` null во всех), и полностью одинаковые строки бывают — две
  штуки товара идут двумя строками. Ключ = устойчивые поля + порядковый номер среди одинаковых
  (`journalKeys` — теперь в `src/modules/finance/ym-journal.ts`, скрипт импортирует её оттуда). Поля выплаты (`paymentStatus`, `bankOrder*`, `bankSum`) в ключ не входят: они
  дописываются, когда Маркет платит. Порядок строк между прогонами разный, содержимое — то же
  (`--compare` дал 0 исчезнувших и 0 новых из 21 663).
- `united-orders` — **снимок состояния заказа**, не журнал (колонка на каждую услугу): годится для
  сверки «выкуплен, а начислений нет», не для дедупа. `goods-realization` — бухгалтерская база с НДС.
- Квота у всех пяти — 100 генераций в час. Скрипт заказывает их строго по одному с паузой,
  `--only` и `--from-dump` нужны, чтобы повторный разбор не тратил квоту вовсе.

### Финансовый журнал: хранилище (M16, TASK-109 → Postgres в TASK-156)

Таблицы `finance_documents` (версия загруженного отчёта за период), `finance_operations` (операция
площадки), `finance_corrections` и `finance_periods` (статус периода, TASK-112) — в Postgres (`src/database/postgres/`), чистые помощники — в
`src/modules/finance/`. Статьи ставит классификатор (раздел ниже).

- **Дубль отсекает база**: unique `(marketplace, telegram_user_id, operation_key)` — индекс в базе, не проверка
  в коде; повторная загрузка того же отчёта не создаёт ни одной записи. Ключ ЯМ —
  `operationKeyOf(journalKeys(rows)[i])` (`ym-journal.ts`), sha256 от `journalKeys`, перенесённой из скрипта
  TASK-108 **без изменения логики**: стабильность между прогонами проверялась именно на ней
  (`scripts/diagnose-finance.ts`), новая функция ключа обнулила бы эту проверку — писать свою нельзя.
- Даты ЯМ («ДД.ММ.ГГГГ ЧЧ:ММ», «ДД.ММ.ГГГГ») — московское время, `parseYmDateTime`/`parseYmDate`.
- **Копейки, а не float рублей** — `bigint` в режиме `number`, целые копейки (`toKopecks`) со знаком как у
  площадки; складываются только копейки. Нечисловая сумма — `null`, а строка без суммы или даты не
  превращается в операцию (бросает). Журнал сверяется с актом до копейки
  (Σ services = −Σ netting, 469 903,39 ₽), а сумма двадцати тысяч float копит ошибку; `integer` кончается
  на 21 млн ₽, годовой оборот продавца в него не влезает. `money.ts` отчётов о заказах остался в рублях.
- **Неизменяемое — только вставкой, изменяемое — `ON CONFLICT DO UPDATE`** (`MUTABLE_ON_CONFLICT` в
  `FinanceOperationRepository`, `upsertMany`): выплата, статья и «где видели последней» обновляются, сумма,
  дата, `raw` и первый `documentId` — никогда. Выплату Маркет дописывает в ту же строку позже — без обновления она не
  дошла бы никогда; обновление всего перетёрло бы `document_id` первой версии и сырую строку, по которым
  разбираются спорные случаи. Вставлена строка или обновлена — `xmax = 0` в `RETURNING`.
- **Версия документа — ответ на пересчёт суммы.** Сумма входит в ключ, поэтому пересчитанная строка — уже
  другой ключ, и upsert оставил бы старую рядом. Изменившийся файл (другой sha256) — версия N+1, тот же
  файл новой версии не заводит: `FinanceDocumentRepository.registerVersion` возвращает прежнюю
  (`created: false`). Снять операции старой версии — дело импорта, в одной транзакции с регистрацией
  версии. Где строку видели последней — изменяемые `period_key`/`last_document_id`:
  по ним находятся строки, выпавшие из новой версии (`findStale`), и помечаются `superseded_at`, а не
  удаляются.
- **Оригинал — `bytea` в строке версии с потолком 15 МБ** (`FINANCE_ORIGINAL_MAX_BYTES`): ZIP журнала за
  месяц в разы меньше. Превышение не роняет загрузку — оригинал не пишется, `original_too_large`
  (`originalTooLarge: true`): операции важнее архива. Выборки версии оригинал не
  тянут (`VERSION_COLUMNS`), скачивание — отдельный `original()`.

### Финансовый журнал: импорт ЯМ (M16, TASK-111)

`FinanceImportService.importPeriod({telegramUserId, period})` (`src/modules/finance/`): generate
`united-netting` в `format=JSON` на весь кабинет → `pollReportFile` → ZIP → лист `transaction_date` →
`journalKeys` + `nettingRowToOperation` → запись. Запуск — очередь `finance-import` или
`scripts/import-finance.ts --user= --month=ММ-ГГГГ` (решение `finance_import_queue_and_script`); расписание —
TASK-112. Период — `finance-period.ts` (`monthPeriod`, `financePeriodKey`).

- **Замена версии — одна транзакция** (`importRows`, общий с ручной загрузкой): `registerVersion` → upsert →
  `findStale` → `markSuperseded` → корректировки → `markImported`. Сбой посередине откатывает всё, поэтому версия существует только импортированной, а тот же
  sha256 честно значит «уже разобрано» (`unchanged`, ни одной записи). Разбор ZIP — до транзакции.
- **У united-netting/generate лимит 1 генерация в минуту на кабинет** («Hit rate limit of 1 points per 1 minute …
  for businessId», пойман алертом с прода). Ночной проход заказывает подряд текущий и прошлый месяц, кнопка
  «Загрузить из Маркета» — несколько месяцев, а повторы клиента (1–2–4 с) минуту не пережидают. Поэтому generate
  обёрнут в `generateWithMinuteLimit`: на `YandexRateLimitError` — пауза 65 с и ещё попытка, всего 3. Только этот
  метод: общий `DEFAULT_RETRY` остальным не меняем. Generate данных не меняет — повтор безвреден.
- **Лист `transaction_date` обязателен** (`nettingRowsOf`): нет — ошибка с перечнем пришедших листов, а не
  ноль операций.
- **Выпавшие строки помечаются `superseded_at`, а не удаляются**, и пишется корректировка
  (`finance_corrections`, решение `finance_corrections_collection`): `changed` — у снятой есть новая
  строка того же смысла (`correctionIdentity`: заказ, товар, услуга, тип, источник, акт, дата — без суммы
  и штук), `removed` — пары нет. **Новые строки без пары — не корректировка**: открытый период каждый день
  прирастает, журнал корректировок утонул бы. Вернувшаяся строка оживает (upsert обнуляет снятие).
  Видны владельцу через `GET /api/finance/corrections` (`AdminJwtGuard` на классе, перечисление полей).
- **Строка, попавшая в отчёты двух периодов, принадлежит последнему импортированному** (`period_key` —
  изменяемое поле) и снимается только из него. Известное ограничение, см. known-gaps.
- **FAILED/таймаут Маркета — `ReportGenerationError`**: `pollReportFile` теперь бросает его всем
  потребителям (платежи, «Отчёты Маркета» — текст прежний), и журнал получает reportId, subStatus и
  времена Маркета. DONE без файла — `empty`, версия не заводится.
- **Своя очередь `finance-import`, один `@Process` на concurrency 1, `attempts: 1`** — две загрузки одного
  периода упрутся в уникальный номер версии, а повтор жжёт квоту 100 генераций/час. Payload —
  `{telegramUserId, from, to}`, токена нет: креды из Mongo. Свой `@OnQueueFailed` законен (очередь своя).
  Очередь видна в панели «Очереди» (`QueuesService` знает все `QUEUE_NAMES`).
- **Незнакомые статьи — алерт после фиксации** (`reportUnknownArticles`): сообщаем о том, что правда легло
  в журнал.

### Финансовый журнал: ручная загрузка файлом (M16, TASK-114)

Вкладка «Загрузка» CRM «Финансы» под фичей `finance_upload` (default off, `requires: [finance]`):
продавец загружает отчёт по платежам (united-netting) из кабинета — xlsx, xls или csv — в журнал выбранного
месяца. `POST /api/crm/ym/finance/upload` → `FinanceImportService.importManual`. Разбор —
`ym-netting-file.ts` (лист); дальше тот же путь, что у импорта: `nettingRowToOperation`, классификатор,
upsert, версия документа с оригиналом (`source: 'manual'`, миграция 0007).

- **Только united-netting** (решение `finance_upload_netting_only`). Отчёт об услугах узнаётся по
  заголовкам и получает свой отказ `wrong-report`: его строки — расшифровка тех же удержаний, в журнале услуги
  посчитались бы дважды.
- **Ручная версия только добавляет** (`finance_upload_append_only`, `importRows` с `source: 'manual'`): без `findStale`, корректировок и
  снятия. Кусок месяца не должен выбить из P&L операции API. Пустая выплата из файла не стирает
  записанную (`upsertMany(..., {keepPayment: true})`, COALESCE; тот же флаг у API-батча Ozon —
  `IFinanceJournalBatch.keepPayment`, TASK-184). Строку, которую новая версия Маркета уже
  сняла, файл не оживляет — она пропускается (`skippedSuperseded`). Обратное верно: следующий API-импорт
  месяца — версия в режиме замены, и строки, которых у Маркета нет, снимаются корректировкой.
- **«0 дублей» держит каноническое сопоставление, а не угадывание типов.** `journalKeys` хэширует значения
  как есть (`123` ≠ `"123"`), а образца файла кабинета и типов JSON Маркета у нас нет
  (`finance_upload_no_sample`). Поэтому строке файла, у которой есть операция с тем же
  `canonicalJournalIdentity` (текст обрезан, сумма в копейках, штуки числом, дата моментом), достаётся
  ЕЁ `operation_key` (`matchExistingOperations`, операции — `existingBetween` по датам строк файла).
  `journalKeys` не тронут — на нём проверена стабильность ключей между прогонами.
- **Колонки — по заголовкам из словаря синонимов** (`YM_NETTING_COLUMNS`, `Record` по полю, синонимы
  нормализуются `normalizeHeader`): camelCase API плюс предполагаемые русские подписи, на настоящем файле не
  сверены (known-gaps). Заголовок ищется в первых 30 строках каждого листа. Нет обязательных
  (дата, сумма, тип, источник транзакции) — отказ с перечнем подписей; строка с битой датой или суммой — отказ
  с её номером, а не тихий пропуск. Значения приводятся к форме JSON Маркета: даты `ДД.ММ.ГГГГ ЧЧ:ММ`, суммы
  числом, номера из цифр числом. Excel-дата (серийная) — время на часах, т.е. московское; ISO с поясом
  переводится в Москву; CSV читается текстом
  (`raw`), иначе SheetJS сам угадывает даты, и в windows-1251, если не UTF-8.
- **Месяц выбирает продавец** (`finance_upload_month_picked`) — общий пикер вкладок: отчёт за M несёт
  строки других месяцев, по датам месяц не угадать. Только текущий и 12 прошлых.
- **Синхронно, без фоновой задачи**: разбор и транзакция — секунды на месяц. Сверка, статус и аномалии —
  следом, без ожидания в запросе (`followUp`, не бросает; сверка ходит в Маркет). Гонка с ночным
  импортом того же месяца — 23505 на номере версии → `FinanceImportBusyError` → 409 `FINANCE_IMPORT_BUSY`.
- **Лимит 15 МБ = потолок оригинала**, чтобы файл сохранялся всегда. Перехватчик multer стал фабрикой
  `createUploadInterceptor` (`crm/crm-upload.interceptor.ts`) — прайс на ней же.

### Финансовый журнал: расписание и статус периода (M16, TASK-112)

Ночная загрузка united-netting по продавцу и статус месяца «Предварительные данные» / «Проверено» /
«Есть расхождения» (ТЗ п.4). Правила расписания — `telegram/queue/services/finance-schedule.ts`, Redis —
`FinanceImportScheduler`.

- **Одна повторяемая задача на продавца в очереди `finance-import`, не в `reports`**:
  до TASK-157 `ReportSchedulerService.reconcile` снимал на `reports` всё, чего нет в ReportSchedule, и
  снимал бы эти задачи на каждом старте. `FinanceImportScheduler.reconcile` трогает только свой префикс.
- **id — `finance-<telegramUserId>`, через дефис.** Bull 4 склеивает ключ повторяемой задачи как
  `name:jobId:endDate:tz:cron` и в `getRepeatableJobs` режет по `:` (`_keyToData`). С `finance:111` он
  отдавал id `finance` и cron `Europe/Moscow`: сверка не узнавала своих задач и заводила их на каждом
  старте. Поймано на живом Redis, заглушка очереди хранит id как есть. У рассылок отчётов
  (`report:…`) была та же беда — вылечена в TASK-157 тем же способом (`report-<bot>-<user>-<report>`,
  `report-schedule-id.ts`). Старые `report:…` узнаются только по `job.key` и снимаются первой сверкой.
  Заодно сверка рассылок перестала снимать чужие задачи `reports`: раньше она сносила всё, чего нет в
  ReportSchedule, включая `hosting-reminder`, если его хук отработал первым.
- **Тот же job name `import-finance`, payload — union** (`{from,to}` или `{scheduled: true}`), ОДИН
  `@Process`: второй суммировал бы concurrency (урок TASK-080). Периоды ночного прохода (`scheduledPeriods`:
  текущий и прошлый месяц, по понедельникам ещё позапрошлый; по очереди, порядок — раздел TASK-113 ниже)
  считаются при запуске — повторяемая задача живёт месяцами. Сбой месяца сообщается сам и не роняет остальные.
- **Cron 03:00–05:59 МСК от хэша id** (`financeCron`), а не одна минута: у отчёта квота 100 генераций в час. От хэша,
  а не от места в списке — открытие фичи другому продавцу не двигает чужое время.
- **Кому — одобренные с фичей `finance` (default off) плюс админы из `TELEGRAM_ADMIN_IDS`, только с
  подключённым магазином** (решение `finance_schedule_admins`). Это правило ЯМ; Ozon и WB добавляются по
  подключённому ключу и фиче площадки (`pickFinanceMarketplaces`, порядок ЯМ → Ozon → WB). Сверка задач — при старте и без рестарта:
  `AccessController` после правки `finance` и доступа зовёт `refresh()` — тот не бросает,
  флаг уже записан. Процессор перепроверяет право перед проходом.
- **Незакрытый месяц запрашивается по сегодня, но хранится целым месяцем** (`requestRange`). Ключ
  «с 1-го по вчера» менялся бы каждую ночь, и замена версии периода не срабатывала бы никогда.
- **Статус — таблица `finance_periods`, одна строка на период, пишет `importAndRecord` после каждой
  попытки; правило — чистая `periodStatusOf`** (`finance-period-status.ts`, решение
  `finance_period_status_rule`). «Проверено» значит: месяц закрыт, в последней версии нет строк без
  статьи и корректировок, сверки с заказами (TASK-113) и с отчётом услуг по акту (TASK-158) без находок;
  закрытый с любой находкой — «Есть расхождения»; иначе (в том числе «сверка не сделана») — «Предварительные
  данные». Сбой загрузки статус не гасит, а пишет ошибку: моргнувшая сеть ничего не говорит о данных.
  `unchanged` берёт счётчики версии из базы, а не из прошлой строки статуса — версию мог загрузить скрипт до
  TASK-112. Статус дня — статус его месяца (`dayStatus`).
- **Чего нет**: загрузки заказов и итоговых отчётов — расписание расширится вместе с их импортом.
- **Карточка «📒 Загрузка финансов» на «Очередях»** (`GET /api/queues/finance-import`) строится по заведённым задачам из Redis, а не по
  флагам: она отвечает, что стоит на самом деле. Статусы из Postgres грузятся отдельно, сбой базы
  карточку не роняет (`periodsError`). Фронт тоже грузит её вне общего `Promise.all`.

### Финансовый журнал: «Загрузить из Маркета» по кнопке (`finance_pull`)

Продавец увидел на «Обзоре» нули за неделю с продажами: октябрь не попал в журнал, а экран не отличал «журнал
не загружен» от «продаж ноль». Теперь каждый экран над журналом говорит, что месяц не загружен, и (при фиче
`finance_pull`, default off, `requires: [finance]`) даёт кнопку — `POST /api/crm/ym/finance/pull
{months, marketplace}` → `FinanceImportScheduler.pullNow`.

- **Та же очередь и тот же `@Process`, что ночной проход** — разовая задача `{telegramUserId, from, to,
marketplace}`, импорт — `importAndRecord`, статус месяца пишется как всегда. Второго пути импорта нет.
- **jobId `finpull-<mp>-<user>-<ГГГГ-ММ>`, не `finance-…`**: сверка расписания и карточка «Очереди» узнают свои
  задачи по `finance-` и прочли бы разовую как продавца `pull-…`. Двойной клик, пока задача ждёт, второй не ставит;
  `removeOnComplete/removeOnFail: true` — следующий клик после неё ставит новую. Одна попытка (квота).
- **Право — правило расписания** (`marketplacesFor`: фича `finance` и площадки плюс подключённый ключ); не
  положено — 409 `FINANCE_PULL_NOT_ALLOWED`. Месяцы — те же 13, что у загрузки файлом.
- **Кулдаун 15 минут на месяц от `finance_periods.checked_at`** — от последней ПОПЫТКИ, и неудачной тоже: квота
  united-netting 100 генераций в час на кабинет, её делят ночной проход и все кнопки; сбой Маркета повтором через
  минуту не лечится. Месяц в кулдауне приходит в `cooldown` с временем, остальные месяцы ставятся (202, не 429).
- **Готовность фронт видит по смене `checkedAt` месяца в `GET …/months`**: строка периода пишется после каждой
  попытки. Сравнение «до/после», а не с часами браузера.
- **«Загружен» = есть версия документа (`loaded` в `months`), а не `status !== null`**: первая же упавшая загрузка
  заводит строку периода со статусом «Предварительные данные», а данных нет. Причина сбоя — `error` там же.

### Финансовый журнал: сверка акта с отчётом услуг (M16, TASK-158)

Σ акта в united-marketplace-services = −Σ строк united-netting той же actDate. Правило — `ymActServicesTotalOf`
(`ym-act-breakdown.ts`) и `actFindings` (`finance-reconcile.ts`). Без этой сверки «Проверено» означало только
«нет строк без статьи и корректировок».

- **Правило снято с дампа, а не со спеки**: Σ всех листов, колонка `totalAmount` где есть («Размещение» уже за
  вычетом скидки за лояльность), иначе `servicePrice`; журнал — все живые строки с той же датой акта
  («Начисление» со сторно тоже); «Списание» даты акта не несёт. На дампе
  18-10-2026 оба акта сходятся до копейки: 31.08 — 1 012 356,52 ₽, 30.09 — 469 903,39 ₽.
- **Итог акта хранится в `finance_act_services`** (миграция 0010; суммы по листам, без сырых листов), а не
  считается сверкой: отчёт услуг — квота
  100/ч и минуты Маркета, а сверка идёт и без импорта (`reconcileAndRecord`).
- **Generate отчёта услуг — через `generateWithMinuteLimit`, как united-netting.** Лимит 1 генерация в минуту на
  кабинет: актов в журнале месяца два (M и M−1), ночной проход идёт по месяцам подряд, и второй generate без
  паузы получал `YandexRateLimitError` (прод 26-10-2026: акт без расшифровки и итога, сверка «не проверено»).
- **Один отчёт услуг на акт на импорт, общий с расшифровкой TASK-155.** Заказ — под закрытый акт без итога или с
  `journal_matched = false` (последняя сверка нашла расхождение; флаг ставит `FinanceReconcileService`). Это
  самоизлечение: отчёт, снятый раньше, чем Маркет дописал акт, перезапрашивается. **Сравнивать с журналом в
  импорте нельзя** — первый вариант так и делал и был пойман живым прогоном 18-10-2026: строки акта 30.09 лежат
  и в сентябрьском (−343 276,47 ₽), и в октябрьском (−126 626,92 ₽) отчёте, и сравнение с одним отчётом
  перезаказывало бы отчёт услуг каждую ночь. Итог пишется в транзакции версии журнала, новый итог — с
  `journal_matched = null`.
- **Акты периода** — даты акта живых строк с `period_key` месяца. **Σ журнала — по всему журналу продавца,
  строка целиком** (`actJournalSums`, без развёртки `breakdown`): сводная строка несёт
  `breakdown`, но `amountKopecks` у неё прежний, а строка, которую последний импорт отнёс к соседнему месяцу
  (`period_key` изменяемый), акта не покидает. Соседние месяцы не обязательны — тогда в Σ нет их строк, и акт
  честно не сойдётся.
- **Не сошлось — `act_mismatch` («Есть расхождения»)**, допуск 0 копеек (`finance_reconcile_tolerance`):
  «Акт не сходится с отчётом услуг», `expected` — услуги, `actual` — −Σ журнала, текст с датой акта и разницей.
  Нет итога (отчёта услуг) за акт — не находка, а `unchecked` с датой акта, то есть не «Проверено»: «Проверено»
  без итога было бы тем самым ложным «Проверено». `periodStatusOf` не менялся: оба исхода
  приходят обычной находкой и неполнотой. Карточка «Загрузка финансов» печатает акт и разницу строкой под
  статусом месяца (`actMismatches`, `FinanceDiscrepancyRepository.listByKind`). В аномалии не проецируется: ключ аномалии —
  заказ и поручение, у акта их нет.

### Финансовый журнал: сверка с заказами и выплатами (M16, TASK-113)

`reconcile` (`src/modules/finance/finance-reconcile.ts`, лист) + `FinanceReconcileService`; зовёт
`importAndRecord` после удачной загрузки закрытого месяца; без запроса отчёта — `reconcileAndRecord`
(`scripts/import-finance.ts --reconcile-only`). Находки — `finance_discrepancies`, видны через
`GET /api/finance/discrepancies` (AdminJwtGuard).

- **Пять видов находок**: выкуплен без начислений (ни одной операции `sales` по заказу во всём журнале),
  начисление по несуществующему заказу (orderId денежной операции месяца не нашёлся ни в одном магазине
  кабинета), поручение не сходится (Σ строк поручения с датой выплаты в месяце без группы `reference` ≠
  `bank_sum`, или у строк разные `bank_sum`), строка без статьи и акт, не сошедшийся с отчётом услуг
  (`act_mismatch`, TASK-158, раздел выше).
- **По всему живому журналу продавца, а не внутри месяца.** Окно чтения — по `accrued_at` от M−120 до M+62 дней. Отчёт united-netting за M — выплаченное в M (начисления с
  июля) плюс начисленное в M. Продажа по заказу ложится в M−1 (предоплата: начислено при оплате), M или
  M+1 (постоплата); поручение 05.10 лежит частью в отчёте сентября. На дампе 09-2026 сверка внутри
  месяца дала бы 183 ложных «выкуплен без начислений» — продавец перестал бы читать статус.
- **Без обоих соседей — «не проверено», не «Проверено»** (решение `finance_reconcile_neighbors`): без
  загруженных M−1 и M+1 заказы и выплаты не сверяются — `unchecked` с причиной; строки без статьи сверяются
  всегда. Ложное «Проверено» хуже честной неполноты. Поэтому ночной проход идёт **от текущего месяца к
  старшему** — следующий месяц загружается до сверки прошлого. Кончится квота — пострадает
  еженедельная повторная сверка позапрошлого, а не живые месяцы.
- **Находка при неполной сверке всё равно «Есть расхождения»**: найденное уже найдено. Расхождение не
  блокирует цифры — только помечает период. Сбой сверки (`failed`, `ErrorReporter` с
  `context: finance:reconcile`) импорт не роняет — журнал верен, — но «Проверено» гасит: молчание сверки не
  доказывает чистоту.
- **Допуск 0 копеек** (`RECONCILE_TOLERANCE_KOPECKS`, `finance_reconcile_tolerance`): журнал в целых копейках, полные поручения
  09-2026 сходятся до копейки, а любой допуск прятал бы ровно мелкие удержания.
- **Заказы — `stats/orders` по ВСЕМ кампаниям кабинета, мимо deep_history**
  (`finance_reconcile_orders_source`). Журнал бизнесовый (FBS и FBY разом), а флаг защищает деньги в
  отчётах продавца — сверке нужны только id и статус. united-orders отвергнут: ещё одна генерация из
  квоты 100/ч и минуты ожидания. Магазины — кэш `stores` по business_id, иначе `listStores`; выкупленные —
  `DELIVERED`/`PARTIALLY_DELIVERED` по дате обновления окнами ≤30 дней. Существование — новый фильтр `orders`
  клиента, батчи по 200.
- **Только закрытые месяцы** (`finance_reconcile_closed_only`): у открытого — `skipped`, без запросов. Он всё
  равно «Предварительные данные», а его сверка давала бы шум и лишние запросы каждую ночь.
- **Находка — вывод, не событие**: список периода заменяется целиком (`replacePeriod`), вчерашняя
  находка, которую закрыл догруженный сосед, исчезает. Ссылки на операции — первые 100 id и счётчик
  (у поручения строк тысячи). Счётчик и состояние — в `finance_periods` (`discrepancy_count`,
  `reconcile_state`, `reconcile_note`).

#### Сверка Ozon (M19, TASK-132)

- **Правило одно — `reconcile`, площадка даёт только заказы** (`IReconcileOrders`: «выкуплено в месяце» и
  «существует ли»). Общий путь — `FinanceReconcileService.reconcileMarketplace(scope, …)`; `reconcilePeriod` —
  тот же путь с источником ЯМ (`stats/orders`) и актами. Источник Ozon (`ozonReconcileOrders`,
  `src/modules/ozon/ozon-reconcile-orders.ts`) приезжает в батче журнала (`IFinanceJournalBatch.orders`): Ozon
  уже зависит от финмодуля, обратная зависимость дала бы цикл DI. Нет источника — `RECONCILE_NOT_IMPLEMENTED` (WB).
- **Актов и поручений у Ozon нет**: `acts` не передаётся (сверка актов и `markMatched` — только ЯМ), а
  `bankOrderId`/`paidAt` у строк Ozon пусты — правило поручений находок не даёт. Остаются выкуплен без продажи,
  начисление без отправления и строки без статьи. Заказ строки — `unit_number` отправления или товара (`ozonAccrualToRow`; у сбора продавца это договор, не заказ).
- **Выкуплено в месяце = оформлено в месяце и сейчас `delivered`** (решение `ozon_reconcile_by_created_month`).
  Списки отправлений Ozon фильтруются только по `in_process_at`, даты выкупа в них нет. Так каждое отправление
  сверяется ровно один раз — в месяце оформления; продажа по нему ищется по всему журналу окна (до M+62 дней),
  поэтому правило соседей то же: без загруженного M+1 — «не проверено».
- **Существует = любое отправление (и отменённое) за 120 дней до месяца и сам месяц** — то же окно
  (`RECONCILE_ACCRUED_BEFORE_DAYS`), что берёт журнал; один обход FBS+FBO окнами ≤30 дней на оба вопроса
  (квота на ключ одна). Ограничение: операция месяца по отправлению старше окна (поздний возврат) даст
  ложное «начисление без заказа». Поштучный `posting/get` отвергнут: сотни запросов на месяц ради редкого случая.
- Соседи и находки — со скоупом площадки (`documents.latest`, `liveForReconcile(…, marketplace)`,
  `replacePeriod`): журнал ЯМ сверку Ozon не задевает, и наоборот.

### Postgres для финансов (M16, TASK-156)

Финансы M16–M25 живут в Postgres, всё остальное — в Mongo (решение `finance_postgres`, 2026-10-15).

- **Почему не Mongo, где всё остальное.** Mongo прода — один узел без replica set, транзакций нет. А
  замена версии отчёта периода — это регистрация версии, upsert десятков тысяч операций, снятие выпавших и
  корректировки разом: оборвись она посередине, период остался бы наполовину старым. Второе — финдвижку
  (M18) нужны SUM/GROUP BY по десяткам тысяч строк; `scripts/import-finance.ts` печатает сводку уже так.
- **Drizzle + drizzle-kit, драйвер `pg`** (`drizzle-orm/node-postgres`). Схема — один файл
  `src/database/postgres/finance.schema.ts`; миграции — `drizzle/` (в репозитории и в образе: Dockerfile
  копирует каталог в `/app/drizzle`). Меняется схема — `npm run db:pg:generate`, ручных ALTER нет.
- **Миграции применяет само приложение при старте, не дожидаясь и не падая** (`PostgresLifecycle`). Урок
  `lazyConnection` у Mongo: недоступная база не должна оставлять бота без голоса. Сбой — `ErrorReporter`
  (`context: postgres:migrate`) и строка «Postgres: авария» самопроверки; повтор — рестарт или
  `npm run db:pg:migrate`.
- **Пул ленивый, `connectionTimeoutMillis: 10 000`** — по умолчанию pg ждёт соединения вечно. Обработчик
  `pool.on('error')` обязателен: без него рестарт базы роняет процесс необработанным событием.
- **Чтения журнала — не веером.** Пул — 10 соединений, ждущий запрос падает через 10 с. Статусы месяцев
  (`monthStatuses`) — один `findMany` по `inArray(period_key)`, а не запрос на месяц; площадки в `compare` и
  текущий/прошлый диапазоны в CRM-задачах — по очереди, как периоды налогового года. Довод: годовой диапазон
  давал 13 запросов статуса на `build`, два `build` разом на задачу и до 4 задач crm-jobs — пул кончался, и
  падали чужие простые запросы (прод 26-10-2026: `sales-analytics:summary` и `finance:anomalies` одновременно).
- **`PostgresModule` не `@Global`** — кому нужны финансы, импортирует его явно (FinanceModule, его малые
  соседи `FinanceExpenses`/`Tax`/`Purchases`/`Cashflow`/`ScreenModule`, FinanceAdminModule, HealthModule,
  QueuesModule), как DatabaseModule. Nest держит модуль синглтоном — пул один.
- **Транзакция — через аргумент, а не второй набор методов.** Каждый метод репозитория последним
  аргументом принимает `TFinanceExecutor` (база или `tx`), так импорт складывает их в один
  `db.transaction`. Откат проверен тестом: сбой посреди — ни версии, ни операций, ни корректировок.
- **API репозиториев повторяет прежние Mongo-сервисы** (`upsertMany`, `registerVersion`, `latest`,
  `markImported`/`markFailed`, `record`/`list`) — потребители переехали заменой класса. Документ
  возвращается с `id` (uuid), не `_id`.
- **Самопроверка — своя строка `postgres`**: `SELECT 1` в гонке с `PING_TIMEOUT_MS`, а не флаг
  готовности (у ленивого пула его нет). Упавший Postgres бьёт только по финансам. На «Метриках» — своя
  карточка задержки.
- **Тесты — PGlite в процессе, в CI ещё раз на настоящем Postgres** (решение `finance_postgres_tests`).
  `__tests__/helpers/test-postgres.ts`: задан `TEST_POSTGRES_URL` — своя база `fin_test_<rnd>` на файл
  тестов (схема не годится: внешние ключи миграции квалифицированы `"public"`, а файлы идут параллельно),
  иначе PGlite. Миграции — те же файлы `drizzle/`. Тест гонки двух соединений — только на живом
  (`skipIf`), PGlite — один процесс. `bytea` PGlite отдаёт `Uint8Array`, `pg` — `Buffer`: колонка
  приводит в `fromDriver`, иначе тест и прод видели бы разное.
- `drizzle.config.ts` вне `tsconfig.include` и в `ignores` ESLint — довод `vitest.config.ts`.

- **Сторно — статья услуги, а не доход**: `Начисление · Оплата услуг Маркета` («Скидка за лояльность»,
  «Возврат за …») — та же статья, что у услуги, `reversal: true`; знак «+» уменьшает расход и не становится
  доходом. «Скидка за лояльность» уменьшает плату за размещение (лист placement отчёта услуг), поэтому
  `commission` со знаком «+». Незнакомое «Возврат за …» — тоже `unknown`. «Доставка (средняя миля)» с типом
  «Начисление» — сторно `delivery_to_buyer` (живой импорт 10-2026, в дампе 09-2026 её не было; решение
  `finance_ym_middle_mile_reversal`).

### Финансовый журнал: расшифровка сводной строки акта (M16, TASK-155)

У каждого акта в united-netting одна строка «Удержание · Оплата услуг Маркета» без названия услуги — ~100 тыс.
₽/мес одной суммой. Импорт раскладывает её по листам united-marketplace-services того же акта. Правило —
лист `src/modules/finance/ym-act-breakdown.ts`, хранение и развёртка — `operation-breakdown.ts`.

- **Правило снято с живого кабинета и сходится до копейки на двух актах** (дамп 18-10-2026): сводная строка =
  −Σ `servicePrice` строк «сводных» листов с тем же `actDate` (журнал «ДД.ММ.ГГГГ» → отчёт «ГГГГ-ММ-ДД»,
  `ymActDayOf`). 30.09: −51 852 = подписка + пуши + вывоз +
  обработка ×2 + хранение возвратов; 31.08: −47 203,89 — те же плюс персональный менеджер, приём излишков,
  доставка до склада назначения и CPM-буст. **Набор листов меняется от месяца к месяцу**, поэтому сводные
  листы — явная таблица `YM_ACT_SUMMARY_SHEETS`, а не «где нет заказа»: обработка и хранение возвратов несут
  orderId и всё равно идут сводной строкой. `YM_ACT_ORDER_SHEETS` — листы, удерживаемые по заказу; лист ни
  из одной таблицы — `unknownSheets`. Лист без правила не угадывается — Σ не сходится, разница
  становится частью `unknown` (`sheet: null`), без подгонки, и импорт шлёт алерт (`YmActBreakdownError`,
  `finance:ym-act-breakdown`): Σ частей = сумме строки всегда. Строк акта в отчёте нет — расшифровки нет.
- **Поле на исходной операции, а не строки-части** (решение `finance_act_breakdown_field`). Ключ
  (`journalKeys` не тронут), выплата и поручение у строки одни, поэтому выплаты и сверка поручений не могут
  удвоиться по построению. Разворачивает поле одна `expandBreakdown`, её зовут `liveForPnl` (P&L, «Обзор»,
  unit-экономика, прогноз, аномалии — Σ статей та же, «прочие услуги» распадаются) и `receivableByArticle`.
  Выплаты (`livePaidBetween`, сверка) читают строку целой. Развёртка даёт по строке на статью (части одной
  статьи сложены, id — операции); несходящаяся или битая запись читается строкой целиком (`breakdownOf` → null).
- **Колонка `breakdown` изменяемая, но через COALESCE** (`COALESCE(excluded, текущее)` в upsert): null не
  стирает записанную. Расшифровки нет у ручной
  загрузки (`finance_upload_netting_only` — отчёт услуг в журнал не кладётся) и у импорта, где отчёт услуг не
  загрузился.
- **Отчёт услуг за месяц M несёт только акт M**, а журнал за M — ещё и сводную строку акта M−1, поэтому
  отчёт заказывается за месяц АКТА. И только под акт, у сводной строки которого расшифровки ещё нет
  (`breakdownsByKeys`), заказ — до транзакции; после первой удачной загрузки ночной проход квоту 100 генераций/ч не тратит. Тот же
  журнал повторно (`unchanged`) дописывает недостающую расшифровку (`setBreakdowns`).
- **Сбой отчёта услуг импорт не роняет**: строка остаётся `other_services` целиком, ошибка — в
  `ErrorReporter`. Операции важнее расшифровки.
- **Две сводные строки одного акта не делятся** (FBS и FBY раздельно в живом журнале не встречались): доля
  была бы догадкой. Обе остаются без расшифровки, уходит алерт.
- **Новая статья `subscription`** (решение `finance_act_breakdown_articles`): подписка и персональный
  менеджер. Подпись — «Абонентская плата», потому что слово «подписка» в `src` сторожит
  `subscription-removed.test.ts`. Пуши и CPM-буст → `promotion`, вывоз и хранение возвратов → `storage`,
  обработка → `processing`, приём излишков и доставка до склада назначения → `acceptance`. В P&L — площадка,
  вне налога, в unit-экономике и «Обзоре» — «прочие услуги».
- **Раскрытие статьи в CRM показывает долю**: `byIds` отдаёт части, `toOperationRow(op, article)` ставит
  сумму части и «из …» — иначе Σ раскрытия разошлась бы с итогом статьи.
- Сверка — `diagnose-finance.ts --from-dump`, блок «РАСШИФРОВКА СВОДНЫХ СТРОК АКТОВ»: дампу нужны и netting,
  и services за месяц акта.

### Операционные расходы бизнеса (M18, TASK-121)

Аренда, зарплаты, упаковка, содержание склада, доставка от поставщика, прочее и свои категории продавца
(ТЗ п.3 «Расходы бизнеса»): без них движок P&L (TASK-120) не посчитает операционную прибыль. Таблицы
`finance_expenses` и `finance_expense_categories` — в Postgres рядом с журналом. Код — `expense.domain.ts` (виды,
категории, проверка ввода), `expense-allocation.ts` (`allocate`), `FinanceExpensesService` в `FinanceExpensesModule`.

- **Виды:** `one_off` — день `from_day`, ложится в период целиком; `monthly` — с `from_day` по `to_day` (null —
  без конца).
- **Ежемесячный расход делится по дням СВОЕГО месяца** (решение `expenses_allocation_month_days`): 30 000 ₽ в
  октябре — 30 000 / 31 в день, неделя 05–11.10.2026 — 6 774,19 ₽. Полный месяц даёт ровно сумму; «×12/365»
  отвергнута — календарный месяц не сходился бы с записью. **Округление — на кусок месяца**, не на день:
  31 округление дня дали бы 30 000,01.
- **`allocate` (`expense-allocation.ts`, чистая) — одна на CRM и P&L**, итог, `byCategory` и
  `byExpense` копятся в одном проходе — Σ сходится по построению. Единственная дверь —
  `FinanceExpensesService` в маленьком `FinanceExpensesModule` (только Postgres): тяжёлый FinanceModule
  тянет Маркет и Mongo. P&L берёт расходы только через `FinanceExpensesService.allocatedFor` — второй формулы
  распределения быть не должно. `allocatedFor` читает базу заново — правка расхода видна в следующем расчёте;
  кэша нет намеренно.
- **Предустановленные категории — константа `EXPENSE_CATEGORIES` (шесть), не строки в базе**: подпись одна на
  всех. У записи `category` — ключ предустановленной или uuid своей, FK нет; имя своей уникально без учёта
  регистра и не повторяет предустановленную; удаление занятой своей — 409
  `CATEGORY_IN_USE`. id из адреса проверяется `isUuid` до запроса: Postgres на мусор отвечает ошибкой
  синтаксиса, и 404 стал бы 500.
- **Чужого нет:** каждый запрос репозитория фильтруется по `telegram_user_id`, чужой id — 404.
- **Только CRM** (решение `expenses_crm_only`): раздел аккаунта `/ym/expenses` рядом с «Настройками»
  (`expenses_crm_account_section`), фича `expenses` (default off) — `@RequireFeature` на классе контроллера
  `/api/crm/ym/expenses`. Ключа `MENU` нет, у `featureGate` закрывать нечего. Мутации отвечают полным видом
  раздела, `GET /allocation?from=&to=` — распределение на период для экрана «Расходы» (P&L берёт его через
  `allocatedFor`).
- Сумма вводится рублями (строка или число) и разбирается `toKopecks` журнала — одно правило копеек на финмодуль.
  Хранится копейками bigint, 0 < сумма ≤ 10¹² коп.

### Налоговые настройки (M18, TASK-123)

Режим, ставка и дата признания дохода на продавца (ТЗ п.12) плюс чистая `taxOf` — вход движка P&L
(TASK-120). Таблица `finance_tax_settings` (одна строка на продавца) в Postgres рядом с расходами. Код —
`tax.domain.ts` (режимы, признание, проверка ввода), `tax.ts` (`taxOf`, `TAX_BASE_ARTICLES`), `FinanceTaxService`
в `FinanceTaxModule`. P&L берёт настройки только через `FinanceTaxService.snapshot` и считает налог только `taxOf`.

- **База — доход по реализации ДО комиссий, не выплата площадки.** Маркет удерживает услуги из выручки, и
  налог от перечисленного занизил бы его ровно на комиссию и логистику. В базе — `sales`, `subsidies`,
  `compensations`, `other_income` и `returns` со своим знаком; удержания площадки и `bonus_payment` — нет.
  Какие статьи журнала — доход, решает `TAX_BASE_ARTICLES`: `Record<TFinanceArticle, boolean>`, а не список, — новая статья не
  скомпилируется без решения (довод `DRAFT_FIELD_SET`). Тест пиннит, что в базу входят только статьи
  группы `income`.
- **Ставка — сотые доли процента целым** (600 = 6 %): регионы снижают ставку до долей процента, а
  float-проценты в базе и в сравнении «не выше предельной» дали бы 5,999999. Предельные — 6 % и 15 % (регион
  только снижает), 0 допустим (каникулы). Ввод — проценты, не больше двух знаков после запятой.
- **Дата признания по умолчанию — поступление денег** (`payment`, кассовый метод УСН, решение
  `tax_recognition_payment_default`), иначе `realization`; `taxOf` берёт у строки `paidDay` или `realizedDay`. Строка без нужной
  даты в период не ложится, но считается в `undatedLines` — доход не пропадает молча.
- **Выбираются два режима УСН** (решение `tax_regimes_usn_min`). ОСНО и НПД есть в типе, но отклоняются
  проверкой: сохранённый режим без расчёта молча дал бы ноль налога. У «Доходы минус расходы» —
  минимальный налог 1 % от доходов; по закону он годовой, за месяц в «Финансах» это оценка, а «Налоги»
  года (TASK-146) берут его только у года.
  Расходы к вычету собирает вызывающий (P&L), `taxOf` их не ищет. Формула: база `max(доход − вычеты, 0)`,
  налог `max(база × ставка, 1 % дохода)`, флаг `minimumApplied`. **Округление — один раз, на итог.**
- **Нет строки — действует умолчание ALL BEST WATCH** (`DEFAULT_TAX_SETTINGS`: УСН «Доходы» 6 %, по
  поступлению; `finance_per_seller`, `isDefault: true`), в базу не пишется: хранятся только явные решения. Экран говорит «по умолчанию, сохраните, чтобы подтвердить».
  Смена режима без ставки подставляет общую ставку нового режима — 6 % «Доходов» не переезжают в «Доходы
  минус расходы».
- **Только CRM** (решение `taxes_crm_only`): раздел аккаунта `/ym/taxes` рядом с «Расходами», фича `taxes`
  (default off), `@RequireFeature` на классе `/api/crm/ym/taxes`. Ключа `MENU` нет — `featureGate` закрывать
  нечего. `FinanceTaxModule` — только Postgres, по доводу `FinanceExpensesModule`.
- **Плоская `taxPercent` бота не тронута** — это ставка плоской формулы «Прибыли» от суммы продаж, другой
  вопрос.

### Налоговый модуль ИП (M23, TASK-146)

Вкладка «Год» в CRM «Налоги» (`/ym/taxes/:tab?`) под фичей `tax_year` (default off, `requires: [taxes, finance]`,
решение `tax_year_feature`): доход с начала года, налог и авансы по отчётным периодам, уменьшение на взносы, лимит
УСН и порог НДС, прогноз, сверка с бухгалтерией. Ядро — `src/modules/finance/tax-year.ts` (лист),
`tax-year.domain.ts` и `FinanceTaxYearService`; ввод — `FinanceTaxYearDataService` в `FinanceTaxModule`; доставка —
kind `taxes:year` (scope `account`) и маршруты `crm/ym/taxes/{staff,reductions,reconciliations}`.

- **Налог = «Финансы» по построению.** Каждый отчётный период — `FinanceService.build` с 1 января по конец
  периода, из него `pnl.tax`: тот же `taxOf` на тех же строках. Второй формулы нет, поэтому «Налоги» и «Финансы»
  за тот же период не могут разойтись, и база — доход до комиссий (`TAX_BASE_ARTICLES`), тест это пиннит.
- **Отчётные периоды УСН нарастающим итогом** (Q1, полугодие, 9 месяцев, год; решение
  `tax_year_reporting_periods`), а не месяцы: авансы платятся за Q1/полугодие/9 месяцев, и сверяет бухгалтер
  именно их. Начавшийся период обрезан сегодняшним днём. Аванс = к уплате − к уплате прошлого периода; < 0 — к
  зачёту. Минимальный налог (1 %) — только у года, у авансов — `regularKopecks`: по закону он годовой (закрыта
  оговорка «до TASK-146» в `taxOf`).
- **Уменьшение на взносы — только УСН «Доходы»**, по дню уплаты, нарастающим итогом. Лимит: без работников —
  весь налог, с работниками — `reduction_limit_with_staff_bp` строки года. Строки года нет — уменьшения с
  работниками нет (завысить налог безопаснее, чем угадать долю). В «Доходы минус расходы» взносы — расход.
  Флаг «есть работники» — `finance_tax_settings.has_staff`; форма режима его не трогает (`upsert` без аргумента).
- **Параметры года — строки Postgres (`finance_tax_years`), не код** (решение `tax_year_params_global_admin`):
  лимит УСН, порог НДС, взносы, предельные ставки и лимит уменьшения при работниках меняются законом каждый год.
  Одна строка на год для всех. Миграция 0008 заводит 2025–2027 (`ON CONFLICT DO NOTHING`), правит админ через
  `PUT /api/finance/tax-years/:year` (`AdminJwtGuard`) без деплоя. Ввод — рубли и проценты; не задано — null, и
  экран пишет «не задано», а не считает с нулём. Значения внесены по памяти и помечены «сверить» (known-gaps).
- **Пороги предупреждений — `TAX_YEAR_THRESHOLDS`** (80 % лимита), едут в ответе. Виды: приближается, превышен,
  по прогнозу превысит (лимит УСН и порог НДС), ставка выше предельной года, параметры не заданы, строки без даты.
- **Уплаченный налог не дублируется**: берётся из `finance_tax_payments` раздела «Закупки» за календарный год.
  Уплата не знает своего периода, поэтому остаток года = к уплате − уплачено в году.
- **Сверка — `finance_tax_reconciliations`**: суммы бухгалтера (необязательны) и отметка; расхождение = наше −
  бухгалтерия. `checked_at` ставится при отметке и не сдвигается повторной.
- **Вкладка, не раздел**: `tax_year` в `FEATURES_WITHOUT_SECTION`, `CRM_SECTIONS['ym-taxes']` остаётся `[taxes]`.
  Методы контроллера несут `@RequireFeature(TAXES, TAX_YEAR)` — метод перекрывает классовый (довод аномалий).
- **Прогноз помечен «прогноз»** в ответе (`kind: 'forecast'`) и на экране. Он линейный по дням; у закрытого
  года его нет.

### Финансовый движок P&L (M18, TASK-120)

Реальная прибыль периода из журнала операций, а не сумма выплат (ТЗ п.3): `pnlOf`
(`src/modules/finance/pnl.ts`, чистая) + `FinanceService.build(telegramUserId, period, now)` в `FinanceModule` —
единственная дверь к реальной прибыли периода. Её зовут «Финансы», «Обзор», unit-экономика, аналитика продаж,
рейтинги, сравнение площадок, склад, прогнозы, калькулятор цен, «Налоги» года, аномалии, «фактическая чистая»,
ИИ-инструменты и разбор периода, `scripts/pnl-finance.ts`.

- **Σ статей = чистая по построению.** Один проход копит корзины статей с id операций (`byArticle`) и
  себестоимость по артикулам (`cogs.bySku`), уровни (валовая → после площадки → операционная → чистая)
  складываются только из них. Раздел статьи — `PNL_SECTION`, `Record` по union: новая статья не скомпилируется
  без места в P&L. Выручка = продажи + субсидии + возвраты, прочие доходы = компенсации + прочие начисления,
  расходы площадки — группа `expense`, `unknown` — отдельной строкой «Не распознано», `bonus_payment` —
  справочно, вне уровней.
- **Дата начисления, а не выплаты** (решение владельца `pnl_accrual_date`, день `accruedAt`): выплата —
  денежный поток. Налог — по своей дате признания, поэтому `liveForPnl` отдаёт ещё и выплаченное в периоде,
  начисленное раньше (по статьям базы налога), — `taxOf` фильтрует сам; `paidDay` — день `paidAt`,
  `realizedDay` — день `accruedAt` (`pnl_tax_dates`). Два запроса вместо OR, чтобы шёл частичный индекс по
  `accrued_at`. Вычеты «Доходы минус расходы» = себестоимость + услуги площадки + опер. расходы.
- **Опер. расходы — `FinanceExpensesService.allocatedFor`, налог — `FinanceTaxService.snapshot` + `taxOf`.**
  Второй формулы нет.
- **Себестоимость — по дню строки продажи** (`pnl_cogs_sale_day`): у журнала нет `creationDate` заказа, а
  тянуть его из `stats/orders` — запросы к Маркету на каждый расчёт. Товар двигают ТОЛЬКО «Платёж
  покупателя» (+) и «Возврат платежа покупателя» (−) (`ymGoodsMovement`): возврат баллов — та же статья `returns`,
  и сторно себестоимости по нему вычло бы вернувшийся товар дважды; компенсация за утерю товар не
  возвращает. Закуп — `datedCosts` (тот же, что у «Прибыли»). Штуки — `raw->>'count'`, колонки нет, миграция не
  понадобилась. Закупка партии в журнале не бывает.
- **Нет закупа на дату или числа штук — выручка остаётся** (`pnl_unknown_cost_keeps_revenue`), позиция — в
  `cogs.unknown`, в отличие от `profitOf`: исключи мы заказ, выручка разошлась бы с кабинетом, ради сверки с
  которым P&L и строится. Что чистая завышена, говорит `pnl.unconfirmed` (общий тип из
  `src/shared/profit-confirmation.ts`, раздел «Неподтверждённая прибыль» ниже): заказы и сумма таких продаж; до
  TASK-119 это был голый `complete: false`. Второй «подтверждённой чистой» нет (`profit_unconfirmed_flag_only`); экраны
  печатают признак, а не вычисляют.
- **`unknown` — в чистой, вне налога** (`pnl_unknown_article_in_net`): деньги реально ушли или пришли.
- **Статус** — `combinedPeriodStatus` по месяцам периода из `finance_periods`: расхождение побеждает,
  «Проверено» — только все месяцы; месяц без журнала — «Предварительные данные».
- **Плоская оценка — только текущий месяц** (`pnl_flat_current_month_only`): `ProfitService` знает периоды
  бота, а расширять `IReportPeriod` ради прошлых месяцев — правка общего кода отчётов. Рядом — только для
  непроверенного ТЕКУЩЕГО месяца (`ProfitService.build`, период «с 1 числа», основной блок), с подписью
  «Предварительные данные»; иначе `flat: null` + `flatNote`. Прошлый непроверенный месяц — метка и причина без
  плоской суммы. Сбой Маркета — `ErrorReporter` (`finance:pnl-flat`, без алерта), P&L живёт.
- **`build(..., {flat: false})`** — без плоской оценки: «Обзору» и остальным экранам поверх P&L она не нужна. «К получению» отдельно —
  `FinanceCashflowService.receivable`, его же зовёт `build` ДДС.
- **Заказы и штуки периода** (TASK-125) — `IPnl.ordersCount` (различные `orderId` строк `sales`) и `units`
  (продано − вернулось, включая позиции без закупа) копятся в том же проходе, что корзины.

### «Фактическая чистая» в «💰 Прибыли» (M18, TASK-126)

Бот и CRM печатают рядом с плоской чистой число из журнала (решение `finance_actual_beside_flat`):
период проверен — «📒 Фактическая чистая», нет — плоская помечена «· предварительно» с причиной. Фича
`profit_actual` (default off, `requires: [finance]`, ключа `MENU` нет — модификатор отчёта, в
`FEATURES_WITHOUT_SECTION`). Лист — `src/modules/finance/profit-actual.ts`, дверь —
`FinanceService.actualNet(uid, periodБота, now)`. Период бота → журнал: `financePeriodOf` (`periodBounds` +
`isoDate`), «Всего» → нет периода → «предварительно». Тексты без разметки — там же (`ACTUAL_NET_LABEL`,
`ACTUAL_SCOPE_NOTE` «весь кабинет», `PRELIMINARY_MARK`): их печатают и бот, и CRM.

- **Одна дверь на три канала.** Кнопка (`profit-report.processor`), рассылка (`reports.processor`) и kind
  `profit:profit` зовут `actualNet` — и тот же `build`, что «Финансы», поэтому число совпадает с P&L месяца по
  построению. Флаг считает хендлер (нет записи доступа = админ = открыто) и везёт в payload
  (`IProfitReportJob.profitActual`, старые джобы — выключено); рассылка читает его из своей записи. Без флага —
  текст байт в байт прежний.
- **P&L строится только у проверенного периода** (`verified` по `combinedPeriodStatus` месяцев), и без плоской
  (`flat: false`): плоскую вызывающий уже посчитал; отдаются `pnl.netKopecks` и `pnl.unconfirmed`.
  Непроверенный — `preliminary` с подписью статуса, только статусы месяцев из Postgres. Сбой базы —
  `unavailable` с причиной, `ErrorReporter` с `context: finance:profit-actual`, `alert: false` (базу сторожит
  самопроверка); отчёт не падает. ProfitService FinanceService не
  зовёт — FinanceService сам зависит от него.
- **«Весь кабинет» печатается обязательно**: журнал бизнесовый, а плоская — по открытому магазину.
  Неполный закуп — общей `unconfirmedSummary`, своей формулировки нет.
- **«⏮ Прошлый месяц» (`PERIOD.PREV_MONTH`) — только у «Прибыли»** (решение `profit_prev_month_period`):
  «Проверено» бывает лишь у закрытого месяца, иначе фактическая была бы видна только в «Другом дне».
  Кнопки строит `periodsFor`; открыт при `profit_actual` **и** `deep_history` (`isPrevMonthOpen`) — начало
  прошлого месяца почти всегда старше 30 дней, без архива плоская упала бы. Три барьера: кнопки нет,
  `requiredFeatures` требует обе фичи у `rep:prevmonth:profit` (старая кнопка в чате ловится гейтом),
  `parseReportCallback` отвергает `prevmonth` у других отчётов. В CRM `parsePeriodParams` его не знает, kind
  «Прибыли» передаёт его в `extra` сам; фронт — проп `extra` у `PeriodPicker`, на «Калькуляторе» откат на
  «с 1 числа», ссылка `?period=prevmonth` не принимается. В `SCHEDULE_PERIODS` его нет.

### Закупки и денежный поток (M18, TASK-122)

Закупки партий, уплаченные налоги, ДДС периода, фактические выплаты Маркета и деньги к получению (ТЗ п.3).
Таблицы `finance_purchases` и `finance_tax_payments` (миграция 0005) — в Postgres рядом с расходами; чистые
`purchase.domain.ts` (проверка ввода закупки и уплаты налога) и `cashflow.ts` (`expenseCashDays`, `payoutsOf`,
`cashflowOf`, `receivableOf`), сервисы `FinancePurchasesService` в `FinancePurchasesModule` / `FinanceCashflowService`
в `FinanceCashflowModule`.

- **ДДС = деньги по дням оплаты:** поступления — выплаты Маркета (поручения), выбытия — закупки, расходы
  (разовый — в свой день, ежемесячный — ниже) и уплаченные налоги. Итог — только из корзин.
- **ДДС — по площадке** (`build(uid, period, now, marketplace = 'ym')`, TASK-184): выплаты и «к получению» —
  из журнала площадки, расходы, закупки и уплаченные налоги — кабинета целиком, как в P&L площадки. Ozon:
  `paidAt` ставит раскладка сальдо (`src/modules/ozon/README.md`), без номера поручения — выплата = группа
  строк по дню. WB (TASK-185): выплата — из самой строки отчёта реализации, день — `create_dt` отчёта
  (`wb_payout_by_create_dt`), поручение — `realizationreport_id`, сумма — Σ всех строк отчёта из ответа
  (`wb_payout_bank_order_report`); отчёт на стыке месяцев выплачен целиком, поэтому при незагруженном соседнем
  месяце у выплаты горит `mismatch`. Вызовы без площадки (ИИ-разбор периода, инструмент ИИ) — ЯМ.
- **Закупка — движение денег, а НЕ расход P&L**; её место — только ДДС, в день оплаты. Себестоимость проданного P&L уже берёт по продажам
  (`datedCosts`), и закупка партии там списала бы тот же товар второй раз. Поэтому `pnlOf` и
  `FinanceService.build` её не видят по построению: `FinanceCashflowModule` P&L не импортирует, и наоборот.
  Тест на PGlite пиннит, что `FinanceService.build` до и после вставки закупки возвращает тот же P&L.
- **Выплата — это платёжное поручение, своей строки в журнале у неё нет.** Каждая операция united-netting
  несёт `paidAt`, `bankOrderId` и `bankSumKopecks` (сумма ВСЕГО поручения на каждой строке). `payoutsOf`
  собирает строки по `bankOrderId`, в период — по дню `paidAt` по Москве; сумма — `bankSum`, без неё — Σ строк.
  Σ строк ≠ поручению — флаг `mismatch` на экране, находку пишет сверка TASK-113 (одно правило: денежные
  строки — без группы `reference`).
- **Строки поручения ищутся по всему журналу** — новый частичный индекс `(telegram_user_id, paid_at)` WHERE
  `superseded_at IS NULL`: выплата 05.10 лежит частью в отчёте сентября.
- **«К получению» — на сегодня, не на конец периода**: живые строки с `paid_at IS NULL`, начисленные до
  завтрашнего дня, `SUM … GROUP BY article` в базе. Знак сохраняется (удержание уменьшает ожидаемое),
  `bonus_payment` (группа `reference`) — не деньги и не входит. На конец периода строки, выплаченные позже,
  считались бы «к получению» задним числом.
- **Налог в ДДС — только уплаченный, руками** (решение `cashflow_tax_paid_manual`): авансы УСН платят раз в
  квартал, и начисленный `taxOf` в денежном потоке показал бы деньги, которые ещё не ушли. Начисленный
  остаётся в P&L.
- **Ежемесячный расход в ДДС — целиком, раз в месяц, в число дня начала** (`expenseCashDays`, решение
  `cashflow_monthly_expense_start_day`); 31-е в феврале — последний день месяца. В P&L он по-прежнему делится
  по дням (`allocate`) — то начисление, это платёж; функции разные, потому что вопросы разные.
- **Позиции партии — справка** (решение `purchase_lines_optional`): заданы — Σ штуки × цена обязана
  равняться сумме, иначе 400 под полем `lines`. На себестоимость не влияют: закуп товара — прайс и CostHistory.
- **Только CRM** (решение `purchases_crm_section`): раздел аккаунта «Закупки» `/ym/purchases` под фичей
  `purchases` (default off), `@RequireFeature` на классе `/api/crm/ym/purchases`. Ключа `MENU` нет —
  `featureGate` закрывать нечего. Каждый запрос репозитория фильтруется по `telegram_user_id`, чужой или
  не-uuid id — 404. ДДС с выплатами и «к получению» жил тут вкладкой и в TASK-124 переехал в
  «Финансы» целиком (`finance_crm_cashflow_moved`; `src/modules/crm/README.md`, раздел «Финансы» в CRM); старый адрес `/ym/purchases/cashflow` —
  редирект.
- **Пресеты периода — общие с «Расходами»**: `presetRange`/`moscowToday`/`formatDay` переехали в
  `web/crm/src/shared/utils/days.ts`, «Расходы» их реэкспортируют — «этот месяц» не может значить на двух
  экранах разное.

### Аномалии финжурнала (M24, TASK-149)

Детерминированный детектор, не ИИ: чистая `detectAnomalies` (`src/modules/finance/finance-anomalies.ts`, лист) +
`FinanceAnomalyService`, зовётся после сверки в `importAndRecord`/`reconcileAndRecord`. Вкладка «Аномалии»
в CRM «Финансы» под фичей `finance_anomalies` (default off). Входы собирает `FinanceAnomalyService`: живые операции
от начала истории до конца месяца одним `liveForPnl`, P&L месяца через `FinanceService.build({flat:false})`, все
находки сверки месяца — `FinanceDiscrepancyRepository.allOfPeriod`.

- **Семь видов, пороги — один объект `ANOMALY_THRESHOLDS`** с причиной у каждого числа: скачок доли комиссии
  с эквайрингом (≥ 3 п.п. И ×1,25 к медиане до 6 прошлых месяцев, нужно ≥ 3 месяца с выручкой ≥ 10 000 ₽),
  двойные начисления, логистика на товар (×3 к медиане товаров месяца И ≥ 150 ₽/шт, не меньше 5 товаров),
  штрафы и нераспознанные строки (любые, по подписи «тип · услуга»), находки сверки, нет закупа.
  Числа стартовые, на живых данных не калибровались (known-gaps). Новый вид — строка в `ANOMALY_KINDS` и
  `ANOMALY_KIND_LABEL` (`Record`), порядок массива — порядок на экране.
- **Комиссия — статьи колонки `commission` unit-экономики** (`SKU_COLUMN_OF`, с эквайрингом), выручка — раздел
  `revenue` P&L (`PNL_SECTION`): второй классификации нет.
- **Дубли — только расходы и только по заказу**: группа ≥ 2 расходных строк с заказом при равных статье, типе,
  услуге, заказе, артикуле, сумме и дне по Москве. Две одинаковые строки продажи — это две штуки, `journalKeys`
  различает их номером намеренно. И группа услуги с артикулом не дубль, если штук этого артикула в заказе не
  меньше, чем строк: услуга могла начисляться за штуку.
- **Находки сверки проецируются, а не пересчитываются**; `unknown_article` сверки — нет: его ловит свой
  детектор с разбивкой по подписи, иначе одна строка была бы двумя аномалиями.
- **Список — вывод, а не событие** (довод сверки): `replacePeriod` заменяет месяц целиком (`finance_anomalies`,
  unique по ключу) в одной транзакции и ставит `finance_periods.anomalies_checked_at`. Выход отсортирован по виду
  и ключу: порядок строк из базы на результат не влияет (тест). Без этой отметки экран не отличил бы «не проверялся» от
  «аномалий нет».
- **«Просмотрено» — своя таблица `finance_anomaly_reviews` по устойчивому ключу И отпечатку** (решение
  `finance_anomaly_review_fingerprint`). Ключ — `вид:период:идентичность`, без uuid строки, иначе перезамена
  стирала бы отметку каждую ночь. Отпечаток — сумма и число операций: новый штраф того же вида снимает
  отметку сам: отметка действует, пока отпечаток совпал, перезаменой списка не трогается. Отметить можно только
  ключ своей аномалии — чужой и выдуманный молча не находятся.
- **Считается для всех, кому идёт загрузка**: только Postgres и закуп из Mongo, Маркет не спрашивается. Фича
  закрывает показ. Сбой детектора — `ErrorReporter` (`finance:anomalies`), импорт и статус периода не падают.
- **Маршруты повторяют `finance`**: `@RequireFeature` метода перекрывает классовый (`getAllAndOverride`),
  поэтому `GET anomalies` и `POST anomalies/review` несут `(finance, finance_anomalies)`. Фича — в
  `FEATURES_WITHOUT_SECTION`: раздела нет, есть вкладка (решение `finance_anomalies_tab`); `ym-finance` в
  `CRM_SECTIONS` остался `[finance]` — any-of открыл бы раздел, который гвард класса закрывает.
- **`YM_NETTING_REPORT_TYPE` переехал в `finance-period.ts`** (лист) с реэкспортом из импорта: импорт теперь
  зовёт детектор, детектор — `FinanceService`, а тот брал константу из импорта — файлы замкнулись бы в цикл,
  и Nest получил бы `undefined` вместо класса.
- `npx ts-node scripts/anomalies-finance.ts --user=<id> --month=MM-YYYY [--write]` — тот же сервис; без
  `--write` только печатает.

### Неподтверждённая прибыль (M17, TASK-119)

Один признак `IUnconfirmedProfit` (`src/shared/profit-confirmation.ts`, лист без импортов: фронт CRM
берёт его относительным путём, как `price-calc.ts`) в результате ОБОИХ движков: `IProfitTotals.unconfirmed`
и `IPnl.unconfirmed`. До этого «Прибыль» отдавала три разрозненных поля (`excludedOrders`,
`excludedRevenue`, `unknownSkus`), P&L — голый `complete`, и каждый экран собирал пометку сам: «Обзор»
писал её без числа и суммы, «Финансы» — только число артикулов, Unit-экономика считала фильтром на фронте.

- **Поля заменены, а не дополнены** — так компилятор назвал всех потребителей (довод `items` → `sales`).
  `confirmed` не передаётся, а выводится в `unconfirmedOf` из счётчиков: вызывающий не может сказать
  «подтверждено» при ненулевом числе заказов.
- **Смысл у движков разный, признак один.** У «Прибыли» заказ без закупа на дату (или без услуг
  калькулятора) исключён целиком — в чистой его нет, тест это пиннит. У P&L выручка остаётся
  (`pnl_unknown_cost_keeps_revenue`), и признак значит «чистая завышена». Второй «подтверждённой чистой» в
  P&L нет — решение владельца `profit_unconfirmed_flag_only` (2026-10-17): вычет товаров с
  `costKnown: false` выкидывал бы товар целиком при частично известном закупе.
- **P&L считает заказы, а не строки**: различные `orderId` строк продажи без закупа (строка без заказа —
  сама по себе), сумма — их `amountKopecks`. Возвраты не вычитаются: вопрос — какая часть проданного
  посчитана без себестоимости.
- **Деньги — копейки.** `profitOf` округляет исключённую выручку один раз, на выходе.
- Текст — `unconfirmedSummary` / `UNCONFIRMED_PROFIT_LABEL` из того же листа; у «Калькулятора» причина
  своя (`TARIFF_EXCLUDED_REASON`, закуп или категория). `pnl-sku.ts` `costKnown` остался: это поле строки
  разреза, которое считает движок, а не экран.
