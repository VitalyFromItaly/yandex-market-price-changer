# 📱 Telegram-модуль

Боты, обработчики, контроль доступа и очереди. Наружу торчит один HTTP-эндпоинт — приёмник вебхуков.

## 🏗️ Структура

```
telegram/
├── bots/
│   ├── bot-registry.service.ts        поднимает по Telegraf на каждый документ Bot
│   ├── price-changer-bot/
│   │   ├── price-changer.composer.ts  ЕДИНСТВЕННЫЙ источник порядка регистрации
│   │   ├── handlers/                  @Injectable()-синглтоны с методом register(bot)
│   │   ├── menu.constants.ts          подписи кнопок — только здесь
│   │   ├── report-buttons.ts          callback_data кнопок отчётов и рассылки
│   │   ├── help.text.ts               один текст на кнопку и на слэш-команду
│   │   ├── settings.text.ts           то же для экрана настроек
│   │   ├── profile.text.ts            то же для профиля
│   │   └── onboarding.ts              шаги ввода токена и тексты статусов доступа
│   ├── shared/access.domain.ts        чистая логика гейта: canPass, classifyUpdate…
│   └── shared/features.domain.ts      реестр возможностей и пофичный доступ
├── formatting/                        экранирование и разметка сообщений
├── queue/processors/                  обработчики Bull
├── services/                          TelegramService, TelegramApiService, файлы
└── telegram.controller.ts             POST /api/telegram/webhooks/:type/:id
```

## 🤖 Как устроены боты

`BotRegistry` (`OnApplicationBootstrap`) читает документы `Bot` из Mongo — если коллекция пуста,
заводит первый из `TELEGRAM_TOKEN` — и на каждый создаёт `new Telegraf(token, { telegram: { apiRoot } })`,
вешает обработчики через композер и включает приём обновлений.

Способов приёма два, выбирает `TELEGRAM_UPDATE_MODE`:

- `webhook` (по умолчанию) — только `setWebhook`, обновления приходят в наш контроллер.
  `launch({ webhook })` не вызывается сознательно: в telegraf 4.16 он поднимает отдельный HTTP-сервер
  на каждого бота, в который никто не стучится.
- `polling` — `launch()` без опции webhook. Сервера он не поднимает, только опрашивает Bot API через
  зеркало. Нужен там, откуда вебхук недостижим для Telegram (российский хостинг: трафик фильтруется в
  обе стороны). Промис `launch()` не ожидается — он резолвится только после `stop()`, и `await`
  навсегда подвесил бы старт приложения.

`OnApplicationBootstrap`, а не `OnModuleInit`, — чтобы к моменту первого обновления HTTP-слушатель уже
принимал запросы. Остановка polling висит на `OnApplicationShutdown`: иначе старый контейнер при
редеплое продолжает читать обновления, и новый получает `409 Conflict`.

Все исходящие вызовы Bot API идут через **зеркало** из `TELEGRAM_API_URL`. Это одно место, и его
достаточно: telegraf строит от `apiRoot` и вызовы методов, и ссылку на скачивание файла, поэтому
загрузка прайса следует за ним автоматически.

**Обработчики — синглтоны без состояния бота.** Экземпляр `Telegraf` они получают аргументом в
`register(bot)`, поэтому один обработчик обслуживает любое число ботов.

## ⚠️ Порядок регистрации — несущая конструкция

Порядок задан в `price-changer.composer.ts`, и тест `__tests__/unit/composer-order.test.ts` его
фиксирует:

```
accessGate → featureGate → start → menu → slash → adminCallbacks → adminUsers
           → scheduleCallbacks → reportCallbacks → onboardingCallbacks → callbacks
           → apiSettings → stockUpload → fallback
```

- `accessGate` — это `bot.use`, и он обязан быть **первым**: гейт, зарегистрированный после
  обработчиков, не охраняет ничего, потому что обновление до него уже не доходит.
- `featureGate` — сразу за ним и по той же причине. Порядок именно такой: «вас ещё не одобрили»
  объясняет больше, чем «эта функция закрыта», и человеку без доступа второе бессмысленно.
- **Каждый `bot.action` должен стоять до `callbacks`.** `bot.action` — это `on('callback_query')` плюс
  сопоставление образца, и `next()` он не вызывает; общий обработчик переключается по точным строкам,
  а его `default` перезаписывает сообщение — то есть съедает всё, что зарегистрировано после него.
- `ApiSettingsHandler` регистрируется **дважды и намеренно**: `registerCallbacks()` (выбор магазина и
  подсказки онбординга) до `callbacks`, а `register()` (ловля свободного текста) после `menu`/`slash`.
  Одним методом эти два требования не выполнить: попытка слить их обратно уже приводила к тому, что
  выбор магазина отвечал «Неизвестная команда: store_pick:…».

Добавление кнопки reply-клавиатуры стоит трёх правок, и тесты следят за всеми: ключ в `MENU`, ряд в
`MENU_LAYOUT`, `bot.hears(MENU.<KEY>` в `menu-commands.handler.ts`. Кнопке, которая существует только
как inline, ключ в `MENU` давать **нельзя**.

## 🔐 Доступ: одобрение администратором

У каждого пользователя запись `UserAccess` со статусом `new → pending → approved | rejected`.

| Статус     | Что разрешено                                                                         |
| ---------- | ------------------------------------------------------------------------------------- |
| `new`      | `/start` и ввод токена — сам ввод и есть регистрация                                  |
| `pending`  | только `/start`; заявка ушла администраторам                                          |
| `approved` | всё                                                                                   |
| `rejected` | креды стёрты; 24 часа отказ даже на ввод токена, потом статус лениво вернётся в `new` |

- Логика гейта — чистые функции в `bots/shared/access.domain.ts`, они тестируются без telegraf и без
  Mongo.
- Администраторы берутся из `TELEGRAM_ADMIN_IDS` через `AppConfigService.isAdmin(id)` и гейт обходят.
- **Каждый переход статуса — один `findOneAndUpdate` с ожидаемым статусом в фильтре.** Именно это даёт
  «первое решение администратора выигрывает» и идемпотентность заявки без блокировок: проигравший
  просто получает `null`.
- Заявка отправляется на переходе `new → pending`, а не по признаку «креды заполнены»: заполненность
  остаётся истинной и на всех последующих сохранениях, из-за чего прежняя версия слала «🎉 Все
  настройки заполнены!» при каждой правке.
- Переписки через бота нет: в карточке заявки есть `@username`, администратор пишет человеку в
  Telegram напрямую. Поэтому и состояние диалога хранить не нужно.

## 🎛 Пофичный доступ

Одобрение отвечает на вопрос «пускать ли человека в бота», флаги — «какие функции ему открыты».
Реестр живёт в `bots/shared/features.domain.ts` (тоже чистый модуль, без telegraf и Mongo): пять
отчётов по отдельности, `schedule`, две фичи прайса, `promotion` и два FBY-экрана.

| Ключ                                     | Что закрывает                                |
| ---------------------------------------- | -------------------------------------------- |
| `report_shipped_today` … `report_profit` | по кнопке на каждый отчёт                    |
| `schedule`                               | раздел «⏰ Рассылка» и дайджест              |
| `purchase_prices`                        | сохранение закупочных цен из прайса          |
| `stock_update`                           | запись остатков из прайса в Partner API      |
| `promotion`                              | «📣 Продвижение» на экране настроек          |
| `warehouses`, `fby` (default-off)        | экраны склада Маркета, только у FBY-магазина |

- Прежний единый `stock_upload` разделён: закуп и остатки — независимые действия, и админ должен
  уметь закрыть одно, оставив другое. Старые явные записи `stock_upload` в `UserAccess.features`
  инертны — к новым ключам применяется умолчание «включено».
- **Документ гейт не закрывает** (`requiredFeatures({hasDocument}) → []`): исход бывает частичным
  («разобрать файл, но не писать остатки»), а гейт умеет отбить апдейт только целиком. Решение по
  двум фичам принимает `stock-upload.handler` до скачивания файла: обе выключены — отказ, одна —
  соответствующая половина пропускается (`savePurchasePrices` / `stockWriteAllowed` в опциях
  `StockSyncService.sync`, отчёт объясняет через `writeSkipReason: 'feature-disabled'` и
  `purchasePricesSkipped`).
- У `warehouses`/`fby` условий **два**: фича и модель активного магазина FBY. Раскладка
  (`featureMenuLayout(features, placementType)`) вырезает кнопки без любого из условий; модель
  перепроверяют сами хендлеры экранов (кэш `stores`, при пустом — живой `placementFor`), отказ —
  `fbyOnlyScreenText`. Администратор минует фичевый фильтр раскладки (гейт его и так пропускает, а
  записи флагов у него нет), но не условие по магазину.

- Ключи отчётов — это буквально значения `REPORT`: вторая таксономия для тех же пяти вещей
  разъехалась бы, а расписание рассылки и так ключевано ими.
- **Не закрываются никогда**: `/start`, «🏠 Главное меню», «⚙️ Настройки», «❓ Помощь»,
  «📊 Мой профиль», весь визард и админские кнопки. Закрыв их, продавца запирают снаружи собственных
  настроек — без возможности сменить токен или узнать, к кому обращаться.
- Хранится **только явное решение администратора**, поле `UserAccess.features`. Отсутствие ключа —
  не «выключено», а умолчание из реестра (`defaultEnabled`, сейчас у всех `true`). Поэтому миграция
  не потребовалась и существующие продавцы ничего не потеряли.
- `featureGate` (`bot.use`, сразу за гейтом доступа) отбивает кнопки меню и inline-кнопки.
  Свободный текст он не видит, поэтому ответ **датой** на «за какой день?» и **временем** на «во
  сколько присылать?» перепроверяют флаг у себя — `ReportsHandler.run` и
  `ScheduleHandler.handlePendingTime`. Документы он тоже пропускает — их судьбу решает
  `stock-upload.handler` (см. выше).
- Ежедневная рассылка перепроверяет флаг тоже: расписание остаётся в Redis после закрытия
  возможности, и без проверки закрытый отчёт продолжал бы приходить каждый день.
- Кнопки закрытых возможностей из reply-клавиатуры убираются (`featureMenuLayout`), но полагаться на
  это нельзя: подпись можно прислать текстом, а старая inline-кнопка живёт в истории чата вечно.
- Правится всё из веб-панели: раздел «Пользователи» → карточка продавца, тумблеры (`/api/access/*`
  под `AdminJwtGuard`). Там же тумблер самого доступа. В Telegram кнопок для возможностей нет.
- Тексты «доступ открыт» / «доступ закрыт» — в `access-decision.text.ts`, общем у карточки заявки,
  раздела «👥 Пользователи» и веб-панели: три копии одной фразы разъехались бы, и продавец читал бы
  разные объяснения одного события в зависимости от того, откуда админ нажал.

## 📥 Приём прайса

`stock-upload.handler.ts` — единственный путь записи в Яндекс из интерфейса. Кнопки нет: файл
присылается документом в чат.

- Хендлер делает только **быстрые проверки и ставит джобу** `sync-stocks` в очередь
  `file-processing`; скачивание, разбор и запись — в `stock-sync.processor.ts`. Это не оптимизация:
  в режиме polling telegraf не забирает следующую пачку `getUpdates`, пока не завершены все апдейты
  текущей, и синхронная обработка на минуты останавливала бота для **всех** пользователей.
- Проверки идут **до** постановки: форматы `.xlsx`/`.xls`, до 10 МБ, фичи прайса, наличие настроек
  магазина, предупреждение о модели размещения. В payload — `file_id` и флаги, **без токена и без
  буфера**: креды процессор перечитывает из Mongo, файл скачивает сам. Джоба переживает редеплой
  (лежит в Redis; убитая посреди работы возвращается в очередь механизмом stalled-jobs), ставится с
  `attempts: 1` — авто-повтор записи остатков жёг бы квоту Partner API.
- Слово `проверка` в подписи к файлу = сухой прогон. Остатки в Partner API не уходят, но прайс
  сверяется с каталогом, а закупочные цены записываются в нашу Mongo — прибыль считается ещё до первой
  боевой записи остатков.
- Второй файл, присланный пока обрабатывается первый, встаёт в очередь **следом**: джобы идут строго
  по одной, гонки записи нет. Если впереди есть файлы, ответ называет позицию («Перед вами в
  очереди: N»).
- Дальше работает `StockSyncService` из модуля yandex — см. его README.

## ⏰ Очереди Bull

Имена очередей и типы задач — константы в `src/modules/telegram/index.ts` (это файл констант, а не
barrel). Живых задачи четыре:

- **ежедневная рассылка отчётов** (`reports.processor.ts`) по расписанию из `ReportSchedule`;
- **загрузка прайса** — `sync-stocks` в `stock-sync.processor.ts`, см. «Приём прайса» выше (одна
  джоба, а не реанимация мёртвой цепочки);
- **сводка FBY** — `send-fby-overview` в `fby-overview.processor.ts`, очередь `reports`: остатки
  FBY приходят из асинхронного отчёта Маркета (generate → поллинг, до минут). `FbyHandler`
  проверяет фичу и модель, дедупит по очереди (лимит генерации отчёта — 1/мин) и ставит джобу;
  потолок поллинга поднят до ~3 минут, потому что в фоне ждать ничего не стоит;
- **«Прибыль»** — `send-profit-report` в `profit-report.processor.ts`, та же очередь: самый дорогой
  отчёт (два набора заказов оконными запросами, возвраты, калькулятор). Флаг калькулятора считает
  хендлер и кладёт в payload: у администратора нет записи `UserAccess`, и перепроверка в процессоре
  по default-off фиче отбила бы именно его;
- **«🧮 Калькулятор»** — `send-tariff-report` в `tariff-report.processor.ts`, та же очередь и та же
  причина: заказы периода оконными запросами плюс каталог и сам калькулятор тарифов дают на месяце
  десятки секунд.

Из отчётов в очередь уехали **только эти два** — остальные заметно быстрее и остаются в хендлере со
своей защёлкой `inFlight`.

Причина у всех новых одна: polling-цикл telegraf не забирает новые апдейты, пока не завершены
все текущие, — то есть долгая работа в хендлере останавливала бота для ВСЕХ. Ни один из них не
объявляет второй `@OnQueueFailed` на очереди `reports`: этот хук уже принадлежит `ReportsProcessor`,
а второй давал бы двойные записи в журнале.

Живые обработчики очередей берут бота из `BotRegistry.findByTelegramId(botId)` и шлют сообщения
через `bot.telegraf.telegram` — токен в payload не кладётся (он осел бы в failed-джобах Redis).
Схема «**токен бота едет в каждой задаче** + `TelegramApiService.sendMessage(botToken, chatId,
text)`» осталась только у мёртвого конвейера; сам `TelegramApiService` — тонкая обёртка над
`fetch` от того же зеркала `TELEGRAM_API_URL` и единственный собранный руками адрес Bot API в
проекте. Так и должно остаться, иначе один путь начнёт обходить зеркало, пока остальные работают.

> **Цепочка обновления цен мертва** — `PROCESS_FILE → PARSE_FILE → FETCH_YANDEX_DATA →
COMPARE_DATA → UPDATE_YANDEX_OFFERS`. Изменение цен прекращено, обработчики ни в одном модуле не
> зарегистрированы, `handlers/file-upload.handler.ts` не импортируется вовсе. Живые в этом каталоге
> только `reports.processor.ts` и `stock-sync.processor.ts`. Пользовательские тексты в мёртвых файлах
> (про коэффициент цен, CSV, «Скачать пример») читаются как настоящие — не правьте их формулировки,
> они уйдут вместе с кодом.

## 🖼️ Один экран — один текст

Каждый экран, доступный и кнопкой, и слэш-командой, собирается из одного модуля: `help.text.ts`,
`settings.text.ts`, `profile.text.ts`, плюс тексты статусов доступа в `onboarding.ts`. Это не
аккуратность ради аккуратности — все они начинались как две копии, которые молча разъехались: кнопка
справки вела в главное меню, `/settings` предлагал кнопку без обработчика, `/profile` и кнопка
показывали разные поля. `__tests__/unit/screens-single-source.test.ts` читает обработчики как текст и
падает, если какой-то вход перестал звать общий сборщик.

**Никогда не печатайте продавцу `campaign_id` и `business_id`** — он их не вводит, они не нужны ему ни
для чего, а перепутать их легко. Тот же тест это проверяет. Исключение одно — карточка заявки для
администратора, и даже она начинается с названия магазина.

## 🚀 Добавить бота

Расширить `EBotType` в `domain.telegram.ts`, добавить композер и клавиатуру, ветку в `BotRegistry` —
и зарегистрировать новые сервисы обычными провайдерами Nest.
