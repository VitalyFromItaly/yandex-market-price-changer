# Передача остатков (TASK-143)

Сквозной FBS-остаток: продажа со своего склада на одной площадке уменьшает доступный остаток на
остальных. Площадка сама уменьшает остаток при своём заказе, но не знает о чужих заказах, поэтому одно
сквозное число пишется на каждую площадку.

| Файл                                | Что                                                                   |
| ----------------------------------- | --------------------------------------------------------------------- |
| `src/modules/finance/stock-push.ts` | лист: формула, барьеры, отпечаток плана (`stockPushPlanOf`)           |
| `stock-push.service.ts`             | факты для листа (товары, заказы, остатки площадок) и запись (`apply`) |
| `src/modules/crm/stock-push/`       | kind `stock-push:plan`, `POST /api/crm/ym/stock-push/apply`           |
| `web/crm/src/modules/stock-push/`   | раздел CRM `/ym/stock-push`                                           |
| `scripts/preview-stock-push.ts`     | dry-run «что бы записали», ничего не пишет                            |

## Правила

- **Формула** (решение `stock_push_formula_price_minus_sales`): станет = `Product.stock` из последнего
  прайса минус штуки заказов со своего склада (FBS/DBS/EXPRESS) всех подключённых площадок, оформленных
  с дня загрузки прайса. Число всегда в диапазоне `0 … stock`, поэтому выше физического остатка оно не
  бывает.
  - Заказ, оформленный в день загрузки, тоже вычитается: у заказа есть только день, а занизить остаток
    безопаснее, чем завысить.
  - Отменённые заказы не вычитаются, возвраты не прибавляются.
  - FBY/FBO/FBW-продажи свой склад не трогают.
- **Вне плана** остаются товары:
  - без количества в прайсе;
  - отсутствующие в последнем прайсе (их остаток остался с прошлой загрузки, TASK-142);
  - с прайсом старше 28 дней (заказы читаются за 30).
- **Неизвестно = запрещено.** Если не прочитались заказы хоть одной подключённой площадки, запись
  запрещена везде. Если не прочитались остатки площадки, запрещена запись только на неё.
- **FBY/FBO/FBW не пишутся никогда.** Неизвестная модель размещения тоже закрывает запись.
- **Порог обнулений** (решение `stock_push_zeroing_threshold_5`): если на площадке обнулилось бы больше
  5 позиций, на неё не пишется ничего, а админам уходит алерт `stock-push:zeroing`.
- **Пишутся только существующие артикулы.** Артикул, которого нет в остатках площадки, не пишется:
  у ЯМ он отвергает весь батч.
- **Пишут ЯМ, Ozon и WB — каждая площадка за своей фичей** (TASK-175; до него — только ЯМ, решение
  `stock_push_ym_only_write`). Площадка с закрытой фичей записи или без метода записи в реестре —
  источник продаж и просмотр (`no-write-method`).
- **Ozon/WB пишутся только на единственный склад продавца** (решение `stock_push_single_fbs_warehouse`).
  Считаются все рабочие склады продавца на площадке, не только FBS. Складов несколько —
  `several-warehouses`; единственный не FBS (WB DBS, Ozon не `created`) или складов нет — `no-warehouse`.
  Цель тогда называется `<площадка>:<id склада>`, имя — «Ozon · <склад>».
- **WB пишет только карточки с одним штрихкодом** (решение `stock_push_wb_single_barcode`). Многоразмерные
  и без штрихкода не отправляются и попадают в `skipped` итога записи — их остаток на WB не трогается.
- **Запуск — кнопкой** (решение `stock_push_manual_first`) **или по расписанию** (TASK-176, см. ниже).
- **Фичи** — все с `defaultEnabled: false`:
  - `stock_push` открывает раздел и план;
  - `stock_push_write_ym` (`requires: [stock_push]`), `stock_push_write_ozon` (`requires: [stock_push, ozon]`),
    `stock_push_write_wb` (`requires: [stock_push, wb]`) открывают запись своей площадки
    (`STOCK_PUSH_WRITE_FEATURE`). Кнопка видна, если открыта хоть одна.
  - `stock_push_schedule` (`requires: [stock_push]`) — проход по расписанию; без открытой записи хоть
    одной площадки задача не заводится.

## Барьеры записи — где стоят

1. Гвард маршрута: `@RequireFeature(stock_push)` и 403 `WRITE_CLOSED`, если не открыта ни одна
   `stock_push_write_*`.
2. `StockPushService.apply` повторяет эту проверку. План он пересчитывает и пишет только при
   совпадении `planHash`: продавец подтверждал именно эти числа. Пишутся цели без блокировки, чья
   фича записи площадки открыта в снимке features.
3. ЯМ: `StockSyncService.writeStocks` сам выясняет `STOCK_WRITE_ENABLED` и модель по живому
   `listStores()`; последний рубеж — `writeInBatches`, общий с прайсом (повод не писать и
   отрицательные числа — до `getWarehouseId()`).
4. Ozon/WB: возможность реестра `stockWrite.writeStocks` → `OzonStockWriteService` /
   `WbStockWriteService.writeStocks` — единственная функция записи площадки. Внутри по порядку:
   `STOCK_WRITE_ENABLED` (выключен — ни одного запроса), целые неотрицательные количества, склад
   перечитан и это всё ещё единственный FBS с тем же id (иначе `placement`). Запросы записи
   (`OzonSellerClient.updateStocks`, `WbClient.updateSellerStocks`) идут мимо `withOzonRetry` /
   `withWbRetry` — без повторов.

Запись идёт через ту же очередь `file-processing` и тот же `@Process`, что прайс
(`IStockPushJob`, `source: 'push'`), с `attempts: 1`. Каждая запись оставляет строку журнала
`kind: 'stock-push'`.

## Расписание (TASK-176)

| Файл                                                          | Что                                                   |
| ------------------------------------------------------------- | ----------------------------------------------------- |
| `src/modules/telegram/queue/services/stock-push-schedule.ts`  | cron, id задач, кому положен проход (`pickPushUsers`) |
| `src/modules/telegram/queue/services/stock-push.scheduler.ts` | сверка повторяемых задач, «Запустить сейчас»          |
| `stock-push-alerts.ts`                                        | какие блокировки алертить и когда (`blockAlerts`)     |
| `StockPushService.runScheduled`                               | проход: план → алерты → запись → строка журнала       |

- **Каждые 30 минут по Москве** (решение `stock_push_schedule_every_30m`), задача на продавца
  `stockpush-<id>` (дефис — Bull режет ключ по `:`), `attempts: 1`. Сверка — при старте и после правки
  доступа в панели (`refresh` из `AccessController` на `stock_push_schedule`, `stock_push`,
  `stock_push_write_*`, `ozon`, `wb`, одобрение/блок). Админы не планируются: строки доступа нет.
- **Та же очередь `file-processing` и тот же `@Process`** (`source: 'schedule'`, решение
  `stock_push_schedule_file_processing`): прайс, кнопка и расписание пишут остатки по одному.
- **Фичи перечитываются в момент прохода** (`StockPushScheduler.featuresFor`): payload повторяемой задачи
  заморожен. Закрыли — проход оставляет строку «пропущено» и не пишет.
- **План считается один раз** — `runScheduled`, а не `apply(plan.planHash)`: отпечаток сверять не с чем, а
  второй пересчёт удвоил бы чтения площадок. Запись — общий с кнопкой `write()`, барьеры те же.
- **Алерт админам — при смене состояния** (решение `stock_push_schedule_alert_on_change`): блок
  `read-error`, `orders-unknown`, `zeroing`, `no-warehouse`, `several-warehouses` у цели с открытой записью
  алертится, когда появился или сменил причину; держится — тишина, снят — забыт. `placement` и
  `no-write-method` — устройство магазина, не алертятся. Память в процессе: после рестарта один повтор.
  Место ошибки — `stock-push:schedule:<площадка>`.
- **Журнал**: строка `kind: 'stock-push-schedule'` на проход («записано N из M; Ozon «Дом»: …») плюс
  прежние строки `stock-push` на каждую запись. При `STOCK_WRITE_ENABLED=false` проход — dry-run, в строке
  «проверка без записи, позиций N».
- **Карточка «🔁 Передача остатков по расписанию» на «Очередях»** (решение `stock_push_schedule_queue_card`):
  кому заведено, следующий запуск, итог последнего прохода; «Запустить сейчас» — под подтверждением, это
  реальная запись.

## Доводы и история решений

- **Ozon/WB — только единственный склад** (TASK-175). Остаток из прайса — весь товар продавца. Ozon и WB
  хранят остаток по складу и продают сумму складов, поэтому то же число в двух складах удвоило бы
  продаваемое, а делить его по складам нечем. Второй склад любого типа (и DBS у WB) — та же сумма,
  поэтому в счёт идут все склады, а не только FBS. Выбор склада в CRM отложен, пока таких продавцов нет.
- **Многоразмерная карточка WB не пишется** (TASK-175). Прайс знает один остаток на артикул, WB — по
  размеру (штрихкоду); «всё на первый размер» для одежды и обуви неверно, а неизвестное = не пишется.
- **Запись Ozon/WB — без повторов** (TASK-175), по образцу `postWrite` ЯМ: площадка могла применить
  остаток и не успеть ответить, а повтор вслепую лёг бы поверх уже изменившегося остатка.

- **План пересчитывается в процессоре, а не принимается из браузера.** Между просмотром и нажатием может
  прийти заказ или новый прайс, и тогда записались бы числа, которых продавец не видел. Отказ при
  несовпадении стоит одного нажатия «Обновить», а неверная запись в чужой кабинет не отменяется ничем.
  Это довод `splitByLive` карантина.
- **Своя очередь не заводилась.** «Одна запись остатков за раз» держится только общей очередью и одним
  `@Process`: второй обработчик сложил бы параллелизм (урок TASK-080).
- **`writeStocks` — второй вход в `writeInBatches`, а не своя функция записи.** Барьер env и модели
  стоит внутри единственного места с `updateStocks`, поэтому никакой новый путь его не обходит.
- **Не подключённая площадка продажи не вычитает, и экран это пишет.** Иначе продавец без Ozon не смог
  бы писать вовсе.
- **`findWithPriceListStock`, а не `findWithOwnStock`.** Ноль в прайсе — тоже факт, его надо донести до
  площадок, а «Склад» нули отсекает.
