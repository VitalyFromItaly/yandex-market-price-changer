# Wildberries API (M20)

Клиент WB API, подключение токена (TASK-133), карточки и остатки (TASK-134), заказы (TASK-135),
отчёт реализации (TASK-136). Площадка закрыта фичей `wb` (default off).

## Клиент (`wb.client.ts`)

- **Хост — у каждой категории свой**: `content-api`, `marketplace-api`, `statistics-api`,
  `seller-analytics-api`, `finance-api` и другие (`WB_CATEGORY_HOSTS`), общие методы — `common-api`.
  Как хосты сверены — в «Доводах» ниже.
- **Авторизация — `Authorization: <токен>` без `Bearer`.** Токен — JWT; на мусор WB отвечает 401
  «token contains an invalid number of segments».
- Токен живёт только в заголовках экземпляра axios. В логи идут метод, адрес, статус и `requestId`,
  никогда `config.headers`. `proxy: false` — переменные окружения прокси не подхватываются.
- **Повторы — `withWbRetry`**: 429 (пауза из `X-Ratelimit-Retry` или `Retry-After`), 5xx и сеть,
  три попытки. Пауза дольше 30 с не ждётся. У `/ping` лимит 3 запроса за 30 с на хост.

## Доводы и история решений

> факт записан один раз, вместе с причиной. Выше — только правила клиента, которых в доводах не было.

### Wildberries: подключение токена (M20, TASK-133)

Клиент и подключение — `src/modules/wb/`, CRM — `src/modules/crm/wb/` (`PUT /api/crm/wb/connection {token}`),
форма — карточка WB на «Подключениях». Фича `wb` (default off, ключа `MENU` нет).

- **Форма токена проверяется до WB** (`parseWbToken`: три base64url-части через точку), истёкший `exp`
  получает свой текст. Подпись проверяет WB.
- **Проверка — `GET /ping` на хосте каждой нужной категории, а не один запрос.** Токен WB открывает
  только категории, отмеченные при выпуске, и у каждой категории свой хост; другого способа узнать,
  какие именно, нет. Набор (`WB_REQUIRED_CATEGORIES`) — «Контент», «Маркетплейс», «Статистика»,
  «Аналитика», «Финансы», то, что нужно TASK-134…136.
  - Отказ на всех — токен не работает, `WB_TOKEN_REJECTED`.
  - Отказ на части — `WB_TOKEN_SCOPES` с перечнем названий из кабинета WB: продавцу нужно
    перевыпустить токен с галочками, а не «попробовать позже» (урок TASK-077).
  - Сеть, 5xx или 429 после повторов → 503 `WB_UNAVAILABLE`: о токене такой сбой ничего не говорит.
  - Отказ токена пишется в журнал без алерта, недоступность WB — с алертом.
  - При любом отказе база не тронута: неверный токен не перетирает рабочий.
  - Повторная проверка («Проверить связь») — тот же `verify`. Нехватка категорий там — статус `empty`.
- **Название кабинета — `GET common-api/api/v1/seller-info`.** Сбой здесь подключение не отменяет.
  `sid` хранится в `accounts`, но на экраны не выводится.
- **Хосты сверены ответами самих хостов** 18-10-2026: все хосты с `/ping`, без токена — 401 (а не 404) на
  всех десяти. dev.wildberries.ru автоматику не пускает (HTTP 498), поэтому пути сверены ответами хостов.
- **Своей env нет**: хостов десяток, переопределять их по одному никому не нужно. Нужен будет
  прокси — по образцу `POLZA_AI_PROXY_URL`.
- **В реестре у WB подключение, каталог, остатки, заказы и финансы** (`WbMarketplaceAdapter`,
  TASK-162/134/135/136) — довод `ozon_adapter_after_finance`: возможности, которой нет, нет и в реестре,
  поэтому каждая появлялась вместе со своей задачей. «Проверить связь» идёт через его `connection.check`.
- Ошибки — `WbApiError` и наследники, `source: 'wb'` по классу в `ErrorReporter`, фильтр «Wildberries» в
  журнале админки.

### Wildberries: карточки и остатки (M20, TASK-134)

Карточки и остатки WB — только чтение; в WB пишется только остаток FBS из «Передачи остатков» (TASK-175, ниже)
(`WbCatalogService`, `src/modules/wb/`),
карточки привязываются к тем же `Product`, что ЯМ и Ozon, тем же `ProductMatchService.syncCatalog(uid, 'wb',
rows)`: карточка без пары — в очередь, мастер-поля товара не трогаются, ставится только привязка. Токен
читается на каждый вызов через `credentialsOf` (`wbSellerClient`); нет токена — `WbNotConnectedError`, в
реестре — `no-credentials`. Возможности `catalog` и `stocks` в реестре; CLI —
`npx ts-node scripts/sync-ozon-catalog.ts --user=<id> --marketplace=wb [--write]`.

- **Общая часть не менялась ни строкой.** `createMissing` уже `false` для всех, кроме ЯМ, а
  `ProductService` для не-ЯМ пишет только `salePrices.<площадка>` — `ozon_catalog_no_master_overwrite`
  действует для WB по построению, без отдельного решения.
- **Карточки — `POST content-api/content/v2/get/cards/list`**, по 100, курсор `{updatedAt, nmID}` до
  страницы меньше лимита; повтор курсора останавливает обход. Строки — `wbCatalogRows` в
  `products/product.domain.ts`.
- **Ключ карточки — `vendorCode`, артикул продавца** (довод `ozon_card_key_offer_id`): его задаёт продавец.
  `nmID` и `chrtID` клиент отдаёт тоже — их несут заказы и отчёт реализации (TASK-135/136), как SKU Ozon.
  Артикула производителя у WB нет, уровень `vendorCode` сопоставления не работает; штрихкоды — `sizes[].skus`
  всех размеров.
- **Цены нет**: в карточке WB её нет, она в категории «Цены и скидки», которой нет в
  `WB_REQUIRED_CATEGORIES` (токен её не обязан открывать). `salePrices.wb` не пишется, а не пишется нулём.
- **FBW и FBS — разными методами и без суммы** (`marketplace` и `seller` в `IMarketplaceStockLevels`).
  - FBW — «Статистика» `GET statistics-api/api/v1/supplier/stocks?dateFrom=2019-06-20`: полный снимок по
    складам WB, артикул в строке, `quantity` — доступно. Лимит метода — 1 запрос в минуту.
  - FBS — «Маркетплейс»: склады продавца (`GET marketplace-api/api/v3/warehouses`), затем остатки каждого
    (`POST /api/v3/stocks/{id}` `{skus}`) по штрихкодам батчами по 1000.
  - Штрихкод переводится в артикул по карточкам — другого списка штрихкодов у WB нет, а склад продавца
    отвечает только на заданные. Штрихкод без карточки не учитывается (счётчик в логе).
  - Склады одного места складываются, места между собой — никогда. Резерва WB отдельным числом не
    сообщает — `reserved: null`, как у ЯМ.
- **Пути сверены не по документации** (HTTP 498 для автоматики) и живым токеном не проверены — known-gaps.

### Wildberries: заказы и продажи (M20, TASK-135)

Заказы WB — заказы общего формата `IMarketplaceOrder`, WB зарегистрировал в реестре `orders`. Клиент —
`listSupplierOrders`/`listSupplierSales`/`listFbsOrders`/`fbsOrderStatuses`, сервис —
`WbOrdersService.listOrders(uid, period)` → `IMarketplaceOrders`, маппинг — `wb/wb-orders.ts`. Только чтение.

- **Строка — штука товара (`srid`), а не корзина.** WB отгружает и считает каждую штуку отдельно, у штук
  одной корзины свой статус — довод отправлений Ozon. Корзина — `orderNumber` (`gNumber`). Артикул —
  `supplierArticle` (= `vendorCode` карточки), штук в строке всегда 1.
- **Три источника, один ключ.**

  - «Статистика» `GET statistics-api/api/v1/supplier/orders?dateFrom&flag=0` — все заказы FBW и FBS с ценой
    и `isCancel` (база; `warehouseType` → FBW/FBS);
  - `GET .../supplier/sales?dateFrom&flag=0` — выкуп (`saleID` S…) или возврат (R…) той же штуки;
  - «Маркетплейс» `GET marketplace-api/api/v3/orders?limit=1000&next&dateFrom&dateTo` (unix-секунды) +
    `POST /api/v3/orders/status {orders}` батчами по 1000 — этап FBS (`rid` = `srid`).

  Приоритет — от окончательного: возврат → выкуп → статус FBS (`wbStatus`, при `waiting` —
  `supplierStatus`) → отмена (`isCancel` — «Отменён») → заказ FBW «в пути».

- **Выкуп, отмена, отказ и возврат различимы** (решение `wb_refusal_by_fbs_status`). У FBS отказ при
  получении (`declined_by_client`) — «Возвращается», отмена покупателем (`canceled_by_client`) — «Отменён».
  У FBW статистика их не различает: `isCancel` — «Отменён» (known-gaps).
- **Заказ FBW без выкупа и отмены — «В пути»** (решение `wb_fbw_open_order_in_transit`, статус
  `ordered`): промежуточных статусов статистика не знает, а сборку и доставку ведёт WB — довод FBY
  `PROCESSING`. Незнакомый статус FBS — `unknown` и строка в лог (`WB_STATUS_STAGE`,
  `WB_SUPPLIER_STATUS_STAGE` — `Record` по перечню).
- **Статистика обходится по `lastChangeDate` с первого дня периода**: `dateFrom` у неё — дата
  ИЗМЕНЕНИЯ, поэтому поздний выкуп заказа периода приходит, а заказ, оформленный раньше, отсекает фильтр
  по дню оформления (после обхода). Продажи без заказа в выборке пропускаются. Следующая страница — с
  `lastChangeDate` последней строки; стоп на неполной (< 80 000), дубль стыка схлопывается по `srid`.
  **Полная страница без сдвига даты и исчерпанный потолок в 50 страниц —
  `WbIncompleteResponseError`, а не тихий стоп**: остаток за той же датой не достать ничем, а вернуть
  собранное значит недосчитать заказы молча (довод «неполный ответ — ошибка» у финансов Ozon).
- **Лимит «Статистики» 1 запрос в минуту клиент держит сам**: перед каждым вызовом статистики, кроме
  первого, — пауза 61 с (`WB_STATISTICS_INTERVAL_MS`). `withWbRetry` паузы дольше 30 с не ждёт, и без
  этого продажи после заказов падали бы в 429. Цена — минута на каждый следующий вызов.
- **Продажи — `priceWithDisc`**, цена продавца до СПП: СПП — скидка за счёт WB, как субсидия Маркета в
  «Продажах» ЯМ. Задание FBS без строки статистики — `convertedPrice` (копейки, `/ 100` в рубли) при валюте
  643, иначе null.
- **Окна периода — общие с Ozon**: `marketplaceOrderWindows`/`windowMoments` переехали в
  `marketplaces/order-windows.ts` (Ozon реэкспортирует прежние имена). Задания FBS — окнами ≤ 30 дней.
- **Пути и поля — по памяти** (доки отдают 498 автоматике), живым токеном не проверены — known-gaps.

### Wildberries: отчёт реализации (M20, TASK-136)

Еженедельный отчёт реализации WB (`reportDetailByPeriod`) → тот же журнал `finance_operations`, что ЯМ и
Ozon, тем же `importBatchAndRecord`. Клиент и сервис — `src/modules/wb/` (`listRealizationReport`,
`WbFinanceService.importPeriod(uid, period)`, возможность `finance` в реестре, только чтение), разбор и
классификатор — листы `src/modules/finance/wb-journal.ts` и `wb-articles.ts`. Правила повторены в README
модуля finance (`src/modules/finance/README.md`).

- **Строка отчёта — операция, денежные колонки — `breakdown`** (решение `wb_finance_row_per_rrd`), ключ —
  `rrd_id` плюс сумма, довод Ozon: неизменяемые поля пишутся только вставкой, и пересчёт суммы с ключом по
  одному id потерялся бы. Повтор того же отчёта — `unchanged`, 0 новых.
- **Сумма строки — её вклад в «к перечислению»** (`wb_finance_amount_formula`), поэтому Σ строк недельного
  отчёта = выплата недели, и сверка с кабинетом — одна таблица скрипта импорта. Комиссия — не колонка WB, а
  остаток блока товара до `ppvz_for_pay`: так Σ частей = сумме по построению, а не по совпадению колонок.
  Выручка — `retail_price_withdisc_rub`, цена продавца до СПП: СПП оплачивает WB, довод «Продаж» TASK-135.
- **Хост — «Статистика», а не finance-api**:
  `GET statistics-api/api/v5/supplier/reportDetailByPeriod?dateFrom&dateTo&limit=100000&rrdid&period=weekly`,
  и лимит 1/мин держит тот же `statistics()` клиента. Курсор — `rrd_id` последней строки, стоп на пустом
  ответе (204/[]). Неполный обход по `rrdid` (курсор не сдвинулся или 50 страниц подряд) —
  `WbIncompleteResponseError` («неполный отчёт реализации»), как у заказов: недосчитанная неделя легла бы
  как настоящая.
- **Месяц — по `rr_dt` с запасом запроса ±6 дней** (`wb_finance_period_by_rr_dt`): недельный отчёт пересекает
  границу, а по какой дате WB отбирает строки, не сверено. С запасом и фильтром строка ложится ровно в один
  месяц при любом толковании.
- **Артикул — `sa_name` (= `vendorCode`) → товар → артикул ЯМ**, без запроса каталога WB: артикул уже в
  строке. Ключи закупа — в байтах версии, как у Ozon (`refreshSku`).
- Кабинет (`businessId`) — `sid` продавца из проверки подключения (`accounts[0].id`).
- Нет токена — `WbNotConnectedError` до записи статуса периода.
- **Площадки не смешиваются**: `FINANCE_MARKETPLACES` стал `['ym','ozon','wb']`, чтения по умолчанию — ЯМ,
  P&L WB — `FinanceService.build(…, {marketplace: 'wb'})`. Миграции нет — колонка `text`. Компилятор потребовал
  `FINANCE_REPORT_TYPE.wb` и `COUNT_OF.wb` (`raw->>'quantity'`); правило движения товара в `pnlLineOf` —
  отдельная ветка, которую он НЕ потребовал бы: без неё WB молча шёл бы по правилу ЯМ.
- **Ночной проход**: `pickFinanceMarketplaces` — WB по правилу Ozon (токен, фичи `finance` и `wb`, админ без
  флагов), порядок ЯМ → Ozon → WB. `WbModule` импортирует `FinanceModule` — всё, что поднимает WB, требует
  `POSTGRES_URL`.
- Прогон: `npx ts-node scripts/import-finance.ts --user=<id> --month=MM-YYYY --marketplace=wb` — печатает
  статьи, типы строк и к перечислению по недельным отчётам для сверки с кабинетом.
- Сверки и аномалий у WB нет (`RECONCILE_NOT_IMPLEMENTED`), выплат (`paidAt`) метод не несёт. Путь,
  параметры и поля — по памяти (доки 498); живым токеном не проверены, живой отчёт не загружался —
  known-gaps.

### Wildberries: запись остатков FBS (M22, TASK-175)

Единственная запись в WB — `WbStockWriteService.writeStocks` (возможность реестра `stockWrite`), вызывает её
только «Передача остатков» (`src/modules/stock-push/README.md`) под фичей `stock_push_write_wb`.

- **Склад** — `GET /api/v3/warehouses` с `deliveryType` (1 — FBS). В счёт идут все склады продавца: пишется,
  только если склад один и он FBS (`wbStockWriteTarget`). DBS или неизвестный тип — писать некуда. FBW (склады
  WB) в этом списке не бывают и не пишутся никогда.
- **Штрихкоды** — `barcodesByVendorCode` по карточкам (`listCards`). Пишется только артикул с одним штрихкодом;
  многоразмерный и без штрихкода — `skipped` с причиной (решение `stock_push_wb_single_barcode`).
- **Запись** — `PUT marketplace-api/api/v3/stocks/{warehouseId}` `{stocks: [{sku: штрихкод, amount}]}` батчами по
  1000 через `callWrite` — **без `withWbRetry`**. Успех — 204; любой отказ — ошибка батча, без повтора.
- **Барьеры внутри `writeStocks`**: `STOCK_WRITE_ENABLED=false` — ни одного запроса; отрицательное или дробное
  количество — отмена целиком; склад перечитан и всё ещё тот же единственный FBS — иначе `placement`.
- Путь PUT, `deliveryType` и то, что `sku` — штрихкод (а не `chrtId`), — по памяти, не сверены (known-gaps).
