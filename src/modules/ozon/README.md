# Ozon Seller API (M19)

Клиент Ozon, подключение ключа продавца (TASK-128), каталог и остатки (TASK-129), отправления
(TASK-130) и финансы (TASK-131). Порядок площадок — ЯМ → Ozon → WB (решение `tz_finance_scope`).

## Правила клиента

- **Ключ — пара заголовков `Client-Id` + `Api-Key`, у каждого продавца своя.** Клиент
  (`OzonSellerClient`) создаётся на креды через `OzonClientFactory`, как клиент Partner API на
  токен, и не кэшируется. База — только `AppConfigService.ozonSellerApiUrl`
  (`OZON_SELLER_API_URL`, по умолчанию `https://api-seller.ozon.ru`, только схема и хост).
- **Ключ не логируется.** Он живёт только в заголовках экземпляра axios. В логи идут метод, путь,
  статус и код ответа. `config.headers` не пишется никогда. Тест проверяет логи, ошибку и строку
  журнала `ErrorReporter`.
- **Ошибки — `OzonApiError` и подклассы.** `ErrorReporter` ставит `source: 'ozon'` по классу, как
  `yandex` и `polza`. 401/403 — `OzonAuthError`, 429 — `OzonRateLimitError`, 5xx —
  `OzonServerError`, нет ответа — `OzonNetworkError`, 400/404 — `OzonRequestError` (TASK-196). Тело Ozon —
  `{code: число, message}`.
- **400/404 — не «Ozon сейчас не отвечает».** Ozon ответил, ошибка наша: снятый метод (400 «obsolete method cannot
  be used», 404) или неверное тело. Повтора нет, продавцу — «Ozon отключил метод API…» / «Ozon отклонил запрос…», «мы
  уже знаем» — правда: чтения уходят админам через `ErrorReporter`. Базовый текст `OzonApiError` не тронут.
- **Методы — по официальной OpenAPI-схеме Ozon, не по памяти.** docs.ozon.ru закрыт антиботом; схему берём с
  ежедневного зеркала `github.com/vispar-tech/ozon-seller-api-schema` (`schemas/ozon-seller-api-openapi.json`,
  тег «Новости» — даты отключений). Отключённый метод — новый путь в `OZON_PATHS` с комментарием «Заменил …, тот Ozon
  отключил <дата> (TASK-…)».
- Повторы — в «Доводах» ниже («Ozon: подключение ключа»).

### Ozon: подключение ключа (M19, TASK-128)

Первая живая площадка после ЯМ. Клиент и подключение — `src/modules/ozon/`, CRM —
`src/modules/crm/ozon/` (`PUT /api/crm/ozon/connection {clientId, apiKey}`, фича `ozon`, default off),
фронт — `web/crm/src/modules/marketplaces/` (`/ozon/connection` до TASK-161). С TASK-161 форма — карточка Ozon на
«Подключениях» CRM; там же «Проверить связь» по записанному ключу (`verify` + `markChecked`, ключ не
меняется).

- **Ключ проверяется до записи, через `POST /v1/roles`** (роли и методы ключа). Метод ничего не
  меняет и отвечает на любой действующий ключ (решение `ozon_key_check_roles`). Неверный ключ — 401
  `{"code":16, "message":"Invalid Api-Key…"}`. Запись — только после успешной проверки
  (`OzonConnectionService.connect` → `MarketplaceConnectionService.save`). Отказ, недоступность и
  «ключ без ролей» дают разные коды (урок TASK-077). При любом отказе база не тронута, поэтому неверный
  ключ не перетирает рабочий. Опечатка продавца (401) пишется в журнал без алерта, недоступность Ozon —
  с алертом:

  | Исход                | Ответ                                                              |
  | -------------------- | ------------------------------------------------------------------ |
  | неверная форма полей | 400 `INVALID_OZON_KEY` с `field`                                   |
  | Ozon отверг ключ     | 400 `OZON_KEY_REJECTED`, без алерта админам: это опечатка продавца |
  | у ключа нет ролей    | 400 `OZON_KEY_EMPTY`                                               |
  | Ozon не ответил      | 503 `OZON_UNAVAILABLE`, с алертом                                  |

- **Форма Client-Id проверяется до Ozon** (`parseOzonCredentials`). На нечисловой Client-Id Ozon
  отвечает 400 code 3 (живой запрос 16-10-2026), и продавец получил бы «Ozon не отвечает» вместо
  подсказки под полем. Api-Key проверяется мягко, без шаблона uuid: жёсткий шаблон отверг бы рабочий
  ключ при смене формата.
- **Кабинет — это Client-Id.** `/v1/roles` не отдаёт названия кабинета, а придумывать его нельзя.
  Поэтому `accounts: [{id: clientId, name: ''}]`.
- **Повторяется и сетевой сбой, в отличие от Polza.** Повторяются 429, 5xx и сетевой сбой: 4 попытки,
  паузы 1/2/4 с или Retry-After; Retry-After длиннее 60 с не ждём. Вызовы читающие и бесплатные,
  второй такой же ничего не стоит, а у Polza повтор мог стоить второго оплаченного ответа. Лимиты у
  Ozon — на метод и Client-Id, превышение приходит как 429. `withOzonRetry` написан параллельно двум
  другим, а не обобщает их: те стоят под живыми отчётами и ИИ.
- **В реестре у Ozon только подключение** (`OzonMarketplaceAdapter`, TASK-162). Заказы, финансы и
  товары придут возможностями в TASK-130/131/163. Возможность, бросающая «не реализовано», была бы
  ловушкой для ночной загрузки финансов — поэтому её поля просто нет. Сейчас в `MarketplaceRegistry` у
  Ozon подключение, каталог, остатки, заказы и финансы (TASK-162/163/130/131).
- **`available` площадки зависит от фичи** (решение `ozon_available_needs_feature`).
  `availableMarketplaces` открывает Ozon только при открытой фиче `ozon`, иначе — «скоро». Иначе
  «Обзор» звал бы «подключить» туда, где гейт отвечает 403. Поэтому `GET /api/crm/marketplaces`
  передаёт в сервис снимок фич из `crmUser`.
- **Фича `ozon` (решение `ozon_feature_key`)**: default off, ключа `MENU` нет, у `featureGate` в боте
  закрывать нечего. Своего раздела у Ozon больше нет: с TASK-161 ключ подключается карточкой на
  «Подключениях», а `/ozon/connection` — редирект туда (`src/modules/marketplaces/README.md`,
  «Подключения» в CRM).
  Ozon остаётся в `UPCOMING_MARKETPLACES` до появления данных: табы главной и unit-экономика без
  данных показывали бы пустую площадку как живую.
- **Доступность с прод-хоста не проверена** (known-gaps). Если NL до `api-seller.ozon.ru` не
  достаёт, нужен прокси по образцу `POLZA_AI_PROXY_URL`.

### Ozon: отправления и общий заказ (M19, TASK-130; источник — TASK-196)

Отправления FBS и FBO Ozon — заказы общего формата `IMarketplaceOrder` (`marketplaces/marketplace-adapter.ts`), Ozon
зарегистрировал в реестре `orders`. Клиент — `listFbsPostings`/`listFboPostings` (`/v4/posting/fbs/list`,
`/v3/posting/fbo/list`), сервис — `OzonOrdersService.listOrders(uid, period)` (только чтение), маппинг —
`ozon/ozon-orders.ts`. Снаружи — через реестр: `registry.require('ozon', 'orders')`. Ключ продавца — общий
`ozonSellerClient` (`ozon-seller-client.ts`), там же `OzonNotConnectedError`. Правила повторены в README модуля
marketplaces (`src/modules/marketplaces/README.md`).

- **Заказ стал нашей сущностью, и у ЯМ тоже.** Псевдоним `IReportOrder` не годился: у Ozon нет ни `itemsTotal`, ни
  субсидий, ни подстатусов ЯМ. ЯМ переводится `ymMarketplaceOrder` из тех же функций, что отчёты (`orderTotals`,
  `orderDayIso`), поэтому деньги заказа ЯМ через адаптер = деньги отчётов. Отчёты бота и `orders:*` не тронуты.
- **Строка — то, что площадка отгружает одним номером**: у ЯМ заказ, у Ozon отправление (`id` = `posting_number`,
  `orderNumber` = заказ покупателя). Отправления одного заказа идут с разных складов со своими статусами — склеенные,
  они дали бы заказ «наполовину доставлен».
- **Этапы — 10 этапов ТЗ п.11 плюс `unknown`, лист `src/shared/order-stage.ts`** (фронту и TASK-144). Таблицы — `Record`
  по полному enum площадки: `YM_ORDER_STAGE` + `ymOrderStage` в `report-status-map.ts` (литералы статусов ЯМ живут
  только там, их сторожит тест), `OZON_POSTING_STAGE` в `ozon-orders.ts`. Незнакомый статус — `unknown` и строка в лог,
  а не соседний этап.
  - ЯМ: `PICKUP` — «Доставлен», `DELIVERED` — «Выкуплен»; подстатусы сборки `READY_TO_SHIP`/`SHIPPED` — «Собран» /
    «Передан в доставку»; подстатусы невыкупа (те же, что у «Едет обратно») — «Возвращается».
  - Ozon: `delivered` — «Выкуплен» (отдельного «в пункте выдачи» в списке отправлений нет); «Возвращается/Возвращён»
    статусом отправления не выражаются — возвраты Ozon отдельным методом (TASK-145).
- **Окна — те же `periodWindows` по 30 дней**, хотя FBS принимает год: окно на год — тысячи страниц с одним сбоем на
  всех. «Всего» — последние 30 московских дней, как неявное окно ЯМ. FBS и FBO, окна — по очереди (одна квота на ключ),
  дубль на границе окон схлопывается по `posting_number`. Время окна — с 00:00 по 23:59:59 МСК, в запрос — UTC.
- **Методы — `/v4/posting/fbs/list` и `/v3/posting/fbo/list` с одним контрактом** (TASK-196): тело `{sort_dir: 'ASC',
filter: {since, to}, limit, cursor}`, ответ плоский `{postings, cursor, has_next}`, цена позиции — объект
  `{amount, currency}`. Обход — общий `listPostings` по курсору; тот же курсор по кругу или потолок страниц — ошибка, а
  не обрезанный список (недочитанные заказы занизили бы резерв «Передачи остатков»). Страница — 100, максимум схемы.
  До TASK-196 были `/v3/posting/fbs/list` (`offset`, `result.postings`) и `/v2/posting/fbo/list` (массив в `result`);
  Ozon отключил оба 31.08.2026 — FBS отвечал 404, и план «Передачи остатков» блокировал запись везде, включая ЯМ.
- **Продажи Ozon — Σ цена × штуки рублёвых позиций**; хоть одна без рублёвой цены — `null`, а не ноль.

### Ozon: финансовые операции (M19, TASK-131; источник — TASK-194)

`/v1/finance/accrual/by-day` (начисления за день) + `/v1/finance/accrual/types` (справочник типов) → тот же
журнал `finance_operations`, что у ЯМ, и тот же движок P&L. До TASK-194 источником был
`/v3/finance/transaction/list`; Ozon отключил его 8.09.2026 (официальная спецификация, по Habr — 400
`obsolete method cannot be used`). Тип периода остался `ozon-transaction-list`, иначе загруженные месяцы
разъехались бы с новыми по ключу периода.
Клиент и сервис — `src/modules/ozon/` (`listAccruals`, `listAccrualTypes`, `OzonFinanceService.importPeriod` — за месяц),
разбор и классификатор — листы `src/modules/finance/ozon-journal.ts` и `ozon-articles.ts`, запись — общая
транзакция версии `FinanceImportService.importBatchAndRecord`. Возможность `finance` в реестре; ночной проход
`finance-import` и `scripts/import-finance.ts --marketplace=ozon` ходят через неё. Правила повторены в README
модуля finance (`src/modules/finance/README.md`).

- **Площадки не смешиваются** (решение владельца 2026-10-18). Чтения журнала получили `marketplace`
  с умолчанием `'ym'`, поэтому «Финансы», «Обзор», бот и ИИ видят прежние числа. P&L Ozon —
  `FinanceService.build(…, {marketplace: 'ozon'})` и `scripts/pnl-finance.ts --marketplace=ozon`.
  Сложение — TASK-137; `FINANCE_READY` у ИИ-инструментов остался `{'ym'}`.
- **Одно начисление — одна строка, составляющие — `breakdown`** (решение владельца 2026-10-18). Сумма —
  `total_amount`. У отправления (`POSTING`) части — выручка каждого товара `sale_amount` (`sales` при плюсе,
  `returns` при минусе), комиссия `commission.commission` (итоговая) и услуги `delivery.services[]`; `bonus` и
  `coinvestment` справочные — в сумму не входят. У сборов (`ITEM`, `NON_ITEM`, `CONTAINER_FEES`) части —
  `fees[]` по `type_id`. Σ частей ≠ `total_amount` — остаток частью `unknown` и алерт. Выплата и ключ у
  начисления одни, P&L раскладывает части той же `expandBreakdown`, что сводную строку акта ЯМ.
- **Статья сбора — по `name` типа из справочника**, а не по `type_id`: имя — смысл, id — номер в чужой
  таблице. Тип вне справочника и спорные (SetOff, корректировки, Rfbs\*) — `unknown` и алерт. Имена
  встретившихся в периоде типов входят в байты версии: переименованный Ozon тип переразберёт строки, а
  новый тип где-то в справочнике новой версии каждого периода не заводит.
- **Своего типа операции у начисления нет** — `transactionType` синтетический: `POSTING_SALE` /
  `POSTING_RETURN` по знаку Σ `sale_amount` (так делит их открытый разбор, сверенный автором с отчётом о
  реализации), `POSTING`, `ITEM`, `NON_ITEM`, `CONTAINER_FEES`. Старые строки сохраняют тип операции /v3
  (`transactionType` вставляется один раз), поэтому `OZON_SALE_TYPES`/`OZON_RETURN_TYPES` держат оба словаря.
- **Штуки — `sale_amount / seller_price`** по товарам отправления (`COUNT_OF` в репозитории): количества у
  метода нет. Нет цены у любого товара или частное дробное — штук нет, закуп не угадывается. У старых строк —
  длина `items[]`.
- **Найдено при проектировании, а не в бою: части несут id операции.** `pnl-sales.ts` и `pnl-sku.ts`
  брали штуки и закуп из карт по `line.id`, и комиссия продажи Ozon принесла бы её штуки и закуп ещё
  раз. Теперь они читают карты только у строки с `goods`; у ЯМ строки с товаром расшифровки не
  несут, его числа не изменились (тесты ЯМ не правились).
- **Ключ — `accrual_id` плюс сумма** (до TASK-194 — `operation_id`; по сверке автора Habr 1086658 это тот же
  id, а `total_amount` — тот же `amount`, так что повторный импорт старого месяца даёт upsert, а не дубли).
  Неизменяемые поля пишутся только вставкой
  (`MUTABLE_ON_CONFLICT`), и пересчёт суммы с ключом по одному id потерялся бы. С суммой в ключе он
  становится новой строкой, а старая снимается корректировкой «изменено», как у ЯМ. `journalKeys` на Ozon
  не переносится: у Ozon есть id.
- **Артикул строки — ключ закупа, найденный при импорте**: SKU Ozon → `offer_id` (каталог,
  `IOzonProduct.skus` — все SKU карточки) → товар с этой карточкой → его артикул ЯМ (закуп и история
  себестоимости ищутся по нему), иначе сам `offer_id` (решение владельца). Каталог не ответил — алерт
  `finance:ozon-sku`, строки с сырым SKU. Ключи закупа входят в байты версии, поэтому починенный каталог
  даёт новую версию, а `upsertMany({refreshSku})` переписывает артикул. Иначе тот же ответ Ozon дал бы
  `unchanged`, и сырой SKU остался бы навсегда.
- **Неполный ответ — ошибка**: метод берёт ровно день, курсор `last_id` — с тем же `date` (иначе 400), пустой
  курсор — конец. Счётчика строк нет, поэтому неполнота ловится формой: ответ без массива `accruals`, тот же
  курсор по кругу или потолок страниц — импорт падает, журнал не тронут. Импорт снимает строки периода,
  которых нет в новой версии, и снятие выпавших строк сняло бы настоящие начисления.
- **Дни — последовательно**, по запросу на день: открытые разборы ловили 429 уже на 0,3 rps; повторы с
  `Retry-After` — `withOzonRetry`. Месяц — ~30 запросов на продавца.
- **Период — по дню `date`.** Начисления вне дней периода отбрасываются (страховка: иначе строка на границе
  легла бы в два месяца). Ozon дописывает начисления до ~3 дней задним числом и сторнирует прошлые — ночной
  проход перечитывает текущий и прошлый месяц, этого хватает.
- **Нет ключа — `OzonNotConnectedError` до записи статуса**: «не подключён» — не сбой периода.
- **Сверка с отправлениями (TASK-132)** — та же `reconcile`, что у ЯМ, без актов: батч журнала несёт
  `orders: ozonReconcileOrders(client)` (`ozon-reconcile-orders.ts`). Выкуплено в месяце — оформлено в нём
  (`in_process_at`, по Москве) и `delivered`; существует — любое отправление FBS/FBO за 120 дней до месяца и
  сам месяц. Правила и доводы — `src/modules/finance/README.md`, «Сверка Ozon». Аномалий у Ozon нет — правила ЯМ.
- **Выплаты — раскладкой сальдо (TASK-184, решение `ozon_accrual_migration_and_payouts`).** Выплаты по
  операции API не даёт вовсе. После импорта начислений `OzonFinanceService.assignPayouts` берёт
  `/v1/finance/balance` по ОДНОМУ дню (`balanceOfDay`, `{date_from, date_to}` — один день) от начала месяца по
  сегодня: `total.opening_balance` первого дня — долг Ozon на начало месяца, день с `payments > 0` — выплата.
  Раскладка FIFO (`ozonPaidDays`, `src/modules/finance/ozon-payouts.ts`): выплаты гасят сначала сальдо, затем
  строки месяца по `accruedAt`; `paidAt` = полночь МСК дня покрывшей выплаты. Порог строки — максимум
  накопленной суммы (удержание выплачивается вместе со строками до него); строку, начисленную позже дня
  выплаты, выплата не покрывает; `reference` (бонусы) — вне раскладки. Месяц самодостаточен: строки следующего
  месяца по FIFO встают после всех строк этого. Дни — последовательно и до первого дня, когда покрыто всё.
  - **Запись авторитетна для строк месяца:** непокрытые — `paidAt = null` (выплат до сегодня нет), повтор
    импорта даёт тот же итог. Запускается и при `unchanged` — новые выплаты приходят при тех же начислениях.
  - **`bankOrderId`/`bankSumKopecks` не ставятся:** номера поручения у Ozon нет, а сумма выплаты на
    FIFO-строках с ними не сойдётся — сверка писала бы ложные `payment_mismatch`. ДДС группирует такие строки
    по дню (`payoutGroups`), сумма выплаты = Σ строк.
  - **Батч пишет с `keepPayment`:** начисления выплат не несут, и без флага каждая новая версия обнуляла бы
    `paidAt` до следующей раскладки (`MUTABLE_ON_CONFLICT`).
  - **Сбой сальдо — алерт `finance:ozon-payouts`, журнал как есть** (образец каталога выше): начисления уже
    записаны и важнее, ночной импорт разложит заново. Ответ без `total`/`opening_balance` или в чужой валюте —
    ошибка, а не нули: «выплат не было» вернуло бы перечисленное в «к получению». Знак выплаты — модулем.
  - Читатели: ДДС и «к получению» `FinanceCashflowService.build(…, 'ozon')` (вкладка ДДС Ozon в CRM), налог
    «по поступлению» — общий `paidDay` P&L. Годовой налог (`FinanceTaxYearService`) — по-прежнему только ЯМ.
- **Ночной проход — по площадкам продавца** (`pickFinanceMarketplaces`): ЯМ — прежнее правило, Ozon —
  ключ не `rejected` плюс фичи `finance` и `ozon` (админ — без флагов). Задача на продавца одна,
  процессор проходит ЯМ, затем Ozon (с TASK-136 — ещё WB, по тому же правилу). Снятый ключ —
  `not-connected` без алерта.
- `OzonModule` теперь импортирует `FinanceModule`, поэтому всё, что поднимает Ozon, требует
  `POSTGRES_URL`. Обратного импорта нет: тест границ по-прежнему не пускает финансы к клиенту Ozon.

### Ozon: товары и остатки (M19, TASK-129)

Каталог и остатки Ozon — только чтение; в Ozon пишется только остаток FBS из «Передачи остатков» (TASK-175,
ниже) (`OzonCatalogService.products(uid)` /
`.stocks(uid)`, `src/modules/ozon/`), карточки привязываются к тем же `Product`, что ЯМ, общим `matchCards`.
Ключ — `MarketplaceConnectionService.credentialsOf(uid, 'ozon')` на каждый вызов; нет ключа —
`OzonNotConnectedError`. Правила сопоставления — README модуля products (`src/modules/products/README.md`).

- **Одна запись на все площадки — `ProductMatchService.syncCatalog(uid, marketplace, rows)`**
  (для Ozon — `syncCatalog(uid, 'ozon', ozonCatalogRows(...))`), `syncYmCatalog` стал обёрткой. У Ozon
  `createMissing: false`: карточка без пары — `no_match` в очередь, а не новый товар
  (`product_match_ym_union` касается только ЯМ).
- **Мастер-поля товара пишет только каталог ЯМ** (решение владельца `ozon_catalog_no_master_overwrite`,
  2026-10-16). Проход Ozon ставит привязку и `salePrices.ozon`, и всё: иначе каждый проход перетирал бы
  штрихкоды ЯМ своими, а дописывать их — значит размножать штрихкоды-заглушки, которые у продавца и так
  есть (72 % не GTIN, known-gaps TASK-117).
- **Ключ карточки — `offer_id`** (`ozon_card_key_offer_id`): его задаёт продавец и несут отправления.
  `product_id` и SKU Ozon — внутренние номера; SKU клиент тоже отдаёт (`IOzonProduct.sku`) — его несут
  финансовые операции (TASK-131), а не артикул.
- **Каталог — два метода.** `/v3/product/list` даёт только `product_id`/`offer_id` (пагинация
  `last_id`, `limit` 1000, `filter.visibility: ALL`), `/v3/product/info/list` по `product_id` — название,
  штрихкоды, цену, SKU Ozon. **Батч описания — `OZON_INFO_BATCH` = 100, а не 1000 из спеки**: источники
  расходятся, а лишние запросы дешевле 400 на весь обход (урок offer-mappings ЯМ); живой ответ Ozon на
  каталог не сверен (known-gaps).
- **Остатки — `/v4/product/info/stocks`, пагинация `cursor`.** У каждой карточки `stocks[]` с `type`.
- **FBO и FBS — раздельно и без суммы.** `fbo` лежит на складе Ozon, `fbs` — у продавца; общее число —
  тот же смешанный склад, против которого написано правило FBY read-only (`src/modules/yandex/README.md`).
  Незнакомый `type` не складывается никуда — угаданный склад та же ошибка.
- **Обход не крутится вечно** (`last_id`/`cursor`): стоп на пустой странице, пустом или повторившемся
  курсоре, потолок `OZON_MAX_PAGES`.
- **Ответ читается и из `result`, и с верхнего уровня** — v3 и v4 кладут данные по-разному, а не тот
  уровень молча дал бы пустой список (урок `/returns` ЯМ). id приходят числами и хранятся строками.
- **Каталог и остатки Ozon — возможности реестра** (TASK-163, поверх `OzonCatalogService`, который
  наружу не ходит): отправлений и финансов у Ozon в реестре на тот момент не было
  (`ozon_adapter_after_finance`; пришли в TASK-130/131). Снаружи — `registry.require('ozon', 'catalog' |
'stocks')`, уже нашими сущностями — `ozonCatalogRows` (с `archived`) и `ozonMarketplaceStocks` (FBO →
  `marketplace`, FBS → `seller`, доступно = present − reserved). `marketplace-boundaries.test.ts`
  запрещает импорт сервиса из `finance`, `crm`, `products` и `scripts/`.
- **Фичи нет**: экрана нет, функция живёт в CLI (`scripts/sync-ozon-catalog.ts`) и в админском API
  привязок (`product_matching_no_feature`). Экран «Товары» (фича `products`, TASK-118) проход Ozon не
  запускает.
- Прогон: `npx ts-node scripts/sync-ozon-catalog.ts --user=<telegramUserId>` — без `--write` только
  считает и печатает (процент, конфликты, доля штрихкодов не GTIN, FBO и FBS), с `--write` пишет привязки
  и очередь в Mongo. Ходит через реестр (TASK-163), поэтому поднимает `MarketplacesModule` вместе с
  финансами — нужен `POSTGRES_URL`, как финансовым скриптам; данные Postgres не трогаются.

### Ozon: запись остатков FBS (M22, TASK-175)

Единственная запись в Ozon — `OzonStockWriteService.writeStocks` (возможность реестра `stockWrite`), вызывает её
только «Передача остатков» (`src/modules/stock-push/README.md`) под фичей `stock_push_write_ozon`.

- **Склад** — `POST /v2/warehouse/list` (чтение, с повторами; источник — TASK-196): склады FBS и rFBS продавца,
  ответ `{warehouses, cursor, has_next}`, страница 200, обход по курсору. До TASK-196 — `/v1/warehouse/list`, Ozon
  отключил его 7.04.2026 (400 «obsolete method cannot be used»). Архивный (`disabled`)
  не в счёт; пишется, только если склад один и он `created` (`ozonStockWriteTarget`). FBO — склады Ozon — в
  этом списке не бывают и не пишутся никогда.
- **Запись** — `POST /v2/products/stocks` `{stocks: [{offer_id, stock, warehouse_id}]}` батчами по 100
  (`OZON_STOCKS_WRITE_BATCH`) через `callWrite` — **без `withOzonRetry`**: 5xx, 429 и обрыв не повторяются.
  Ответ построчный: позиция без `updated: true` — не записана, её текст — в ошибках батча.
- **Барьеры внутри `writeStocks`**: `STOCK_WRITE_ENABLED=false` — ни одного запроса; отрицательное или дробное
  количество — отмена целиком; склад перечитан и всё ещё тот же единственный — иначе `placement`.
- Форма ответа складов сверена живым ключом 28.10.2026 (`warehouse_id`, `name`, `is_rfbs`, `status`,
  `warehouse_type: "fbs"`); запись `/v2/products/stocks` живым ключом не выполнялась (known-gaps).

### Ozon: цены для «Установки цен» (M28, TASK-201)

Цены Ozon читает и пишет только `OzonPriceWriteService` (возможность реестра `priceWrite`); вызывает её «Установка
цен» (TASK-202, правила — `src/modules/price-set/README.md`).

- **Чтение** — `POST /v5/product/info/prices` `{filter: {offer_id, visibility: 'ALL'}, cursor, limit: 1000}`, батчи
  артикулов по 1000 (`OZON_PRICES_BATCH`), курсор до пустого (с повторами — это чтение). Берётся `price.price` —
  цена продажи из кабинета; 0 и мусор — `null` (цены нет, а не ноль).
- **Запись** — `POST /v1/product/import/prices` `{prices: [{offer_id, price: '1990', currency_code: 'RUB'}]}` батчами
  по 1000 через `callWrite` — **без `withOzonRetry`**. **`old_price` не шлётся** (решение `price_set_keep_discount`):
  зачёркнутую продавец ведёт сам. Ответ построчный, тот же формат, что у остатков (`mapStocksWrite`): позиция без
  `updated: true` — в ошибках батча с текстом Ozon, сбой всего запроса — ошибка батча, следующие пишутся.
- **Барьеры внутри `writePrices`**: `PRICE_WRITE_ENABLED=false` — ни одного запроса; цена не целая или ≤ 0 —
  отмена целиком (`assertPrices`).
- Формы ответов — по документации Ozon, живым ключом не сверены (known-gaps).
