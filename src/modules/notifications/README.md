# Уведомления продавцу (TASK-152, M25)

Раз в день по каждому продавцу с фичей `notifications` проверяются правила. Итог попадает в центр
уведомлений CRM (`/ym/notifications`), а с фичей `notifications_telegram` ещё и одной сводкой приходит в Telegram.
Запрет «Уведомления не делаем» (`crm_dashboard_markethub`) снят решением `tz_finance_scope`.

## Правила

| Правило                                            | Источник                                                                         | Срабатывает                                                       | Порог по умолчанию                      |
| -------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------- |
| `sales_drop`                                       | P&L площадки (`FinanceService.build`, `flat: false`), 7 дней против предыдущих 7 | выручка упала на N % (база ≥ 10 000 ₽)                            | 30 %                                    |
| `expenses_growth`                                  | то же: доля `−marketplaceKopecks / revenueKopecks`                               | выросла на N п.п.                                                 | 5 п.п.                                  |
| `commission_change`                                | непросмотренные аномалии ЯМ `commission_spike` за прошлый и текущий месяц        | есть                                                              | —                                       |
| `suspicious_withholdings`                          | аномалии `penalty`, `duplicate_accrual`, `unknown_article`                       | есть                                                              | —                                       |
| `product_loss`                                     | `pnl.skus` за 28 дней, только `costKnown`                                        | `netKopecks < 0`                                                  | —                                       |
| `out_of_stock` / `low_stock` / `stock_running_out` | сборка склада, только товары с продажами за 28 дней                              | 0 / < N шт. / ≤ N дней запаса                                     | — / 5 / 14                              |
| `purchase_needed`                                  | `purchaseNeedsOf` по скорости и доступному остатку                               | нужно докупить на N дней                                          | 30                                      |
| `stale_stock`                                      | остаток > 0, продаж за 28 дней нет                                               | одна сводка                                                       | —                                       |
| `stock_value_high`                                 | Σ (доступно × себестоимость)                                                     | ≥ N ₽                                                             | 500 000 ₽                               |
| `returns_growth`                                   | `ReturnsAnalyticsService.build`, 28 дней против 28                               | доля выросла на N п.п. **и** потери выросли (база ≥ 10 проданных) | 5 п.п.                                  |
| `tax_limit`                                        | `FinanceTaxYearService.build(...).taxYear.warnings`                              | `approaching` / `forecast_exceeds` / `exceeded`                   | 80 % (порог самого `taxYearWarningsOf`) |

- **Площадки не смешиваются.** Денежные правила и возвраты считаются по каждой площадке отдельно, предмет события —
  сама площадка (`ozon`, `wb:SKU`). Площадка с закрытой фичей не проверяется.
- **«Доступно»** = свой склад из прайса (`Product.stock`); если прайса нет — наибольший FBS среди площадок (у
  площадок это одни и те же штуки, их не суммируют); плюс склады площадок (FBY/FBO/FBW). Решение
  `notifications_stock_own_plus_marketplaces`.
- Пороги и включение правил продавец меняет в CRM. Правило, которого нет в документе настроек, включено с
  умолчанием, поэтому новое правило в коде не требует миграции.

## Дедуп «до смены состояния»

`SellerNotification` — одновременно запись ленты и состояние. Активное уведомление по (правило, предмет) означает
«уже сказали». `diffNotifications`:

- новое событие или сменился `fingerprint` → прежнее снимается, пишется новое;
- событие пропало → уведомление снимается (`active: false`, `expireAt` через 90 дней, TTL-индекс). Если условие
  вернётся, уведомление придёт снова;
- правило, которое в этом прогоне **не посчиталось**, свои активные не трогает. Причины: детектор упал, журнал
  площадки за окно не загружен, склад собрался с проблемами.

`fingerprint` — грубое состояние без чисел: уровень остатка, уровень налогового предупреждения, `unreviewed`.
Если остаток уменьшился с 4 до 3, уведомление не повторяется. Если он стал 0, уровень `low_stock` сменился на
`out_of_stock` — это новое уведомление.

## Доставка

- **Очередь своя — `seller-notifications`** (решение `notifications_own_queue`). Имя `notifications` занято
  прогрессом загрузки прайса, а на `reports` сверка ReportScheduler снимает чужие повторяемые задачи. На очереди
  один `@Process` с concurrency 1. Payload: `{ telegramUserId, scheduled | manual }`, токена в нём нет.
- **Расписание — время продавца** («ЧЧ:ММ» по Москве, по умолчанию 09:00, решение `notifications_daily_seller_time`).
  Время задаётся тем же `parseScheduleTime`/`toCron`, что у «⏰ Рассылки». Id задачи — `notify-<цифры>` (через
  дефис: Bull режет ключ по `:`). Разовая проверка по кнопке CRM идёт с id `notifynow-<id>`, сверка её не узнаёт.
  Расписание пересверяется при старте, после правки доступа в панели (фичи `finance` и `notifications`) и после
  смены времени в боте или CRM.
- **Админы автоматически не проверяются** (решение `notifications_admins_not_auto`): строки доступа у них нет, флаги
  они обходят. Админ проверяет вручную кнопкой «Проверить сейчас»; процессор запускает такую проверку со всеми
  фичами.
- **Telegram** — только при открытой `notifications_telegram` и включённом тумблере. Сводка уходит в каждый
  одобренный чат продавца через его бота. Ошибка отправки (403 — продавец заблокировал бота) пишется в лог и
  задачу не роняет: уведомления уже лежат в CRM, остальные чаты получают своё.
- Ряд «🔔 Уведомления» в «⏰ Рассылке» стоит на экране, закрытом фичей `schedule`. Продавец без `schedule` меняет
  время только в CRM. Кнопки ряда имеют префикс `ntf:`, гейт — `notifications_telegram` в `requiredFeatures`.

## Доводы и история решений

- **Состояние хранится, а не держится в памяти.** У монитора здоровья `shouldNotify` держит состояние в памяти, и
  рестарт там стоит максимум одного лишнего алерта админу. Продавцу после каждого деплоя пришло бы всё заново.
- **Текст сохраняется готовым.** Лента показывает то, что было сказано в момент события. Если пересчитывать текст
  при показе, старое уведомление «мало остатка: 3 шт.» показывало бы сегодняшний остаток.
- **Сборка склада вынесена из CRM.** Правилам остатков нужны те же числа, что разделу «Склад». Вторая копия сборки
  разошлась бы с первой. `movements: false` пропускает отчёты «в пути/возвраты» — самую дорогую часть, которая
  правилам не нужна.
- **Неполный склад не считается вовсе.** Если площадка не дала остатки или журнал месяца не загружен, «закончился»
  было бы ложью. Правила склада в такой день пропускаются, активные уведомления остаются.
- **Ровно пороговое значение срабатывает** (`atLeast` с допуском 1e-9): 0,25 − 0,2 в плавающей точке — это 0,0499….
